Outbox 패턴 — 물리 아키텍처 & 데이터 흐름

각 서비스 내부의 Outbox 테이블 위치 · Kafka 토픽 · Consumer 전체 구조

IdO 서버 (PostgreSQL)
Q-Sign 서버 (PostgreSQL)
Q-IM 서버 (MariaDB)
Kafka 클러스터
IdO Outbox → Kafka
Q-Sign Outbox → Kafka
Q-IM Outbox → Kafka / HTTP
Kafka → Consumer (구독)
Redis Pre-warming
📌 핵심 원칙: 각 Outbox 테이블은 해당 서비스의 DB 안에 존재합니다. 비즈니스 데이터 INSERT와 Outbox INSERT는 반드시 같은 @Transactional 안에서 원자적으로 처리됩니다. Relay가 Outbox를 읽어 Kafka / HTTPS로 발행하며, FOR UPDATE SKIP LOCKED로 다중 인스턴스 중복 처리를 방지합니다.

🟢 Q-Sign 인증 흐름

  1. ① 요청 사용자 → Q-Sign POST /auth/verify
  2. ② TX auth_result + qsign.outbox 동시 INSERT (같은 @Transactional)
  3. ③ Relay OutboxRelay 500ms 폴링 → findPendingBatch SKIP LOCKED
  4. ④ 발행 KafkaTemplate → qsign.auth.events
  5. ⑤ 갱신 whenComplete 성공 콜백 → outbox PUBLISHED
  6. ⑥ 수신 IdO QsignAuthEventConsumer 구독
  7. ⑦ 캐시 Redis Pre-warming (60,000명 대비)

🔵 IdO-Keycloak 인증 흐름

  1. ① 콜백 Keycloak → IdO GET /callback?code=&state=
  2. ② TX ido.auth_result + ido.outbox 동시 INSERT (?::jsonb)
  3. ③ Relay IdoOutboxRelay 500ms (IDO_OUTBOX_RELAY_ENABLED 확인)
  4. ④ 발행 KafkaTemplate → qsign.auth.events
  5. ⑤ 수신 동일하게 IdO QsignAuthEventConsumer 처리

🟡 Q-IM 사용자 변경 흐름

  1. ① UserMgmtService — 회원 정보 변경 API
  2. ② qim.user UPDATE + qim.outbox INSERT (eventVersion+1, 같은 TX)
  3. ③ OutboxServiceImpl.relayPendingEvents (500ms)
  4. ④ Kafka qim.user.events 발행 (partitionKey=qimUserId)
  5. ⑤ 성공 콜백 → outbox PUBLISHED / 실패 시 30초 후 재시도
  6. ⑥a Q-Sign QimUserEventConsumer → auth_lock 잠금
  7. ⑥b IdO QimSpMemberEventConsumer → 기관 Webhook 전파

🟢 Q-Sign 중복 방어

  1. 중복 체크 isAlreadyProcessed() → processed_event 조회
  2. 버전 역전 isVersionOutdated() → last_event_version 조회
  3. 처리 USER_SUSPENDED → auth_lock 잠금
  4. 완료 markProcessed() + updateLastVersion()

🔵 Handoff + Webhook 흐름

  1. ① 사용자 → POST /handoff/issue
  2. ② HandoffServiceImpl — Outbox 없이 kafkaTemplate 직접 발행
  3. ③ Kafka ido.handoff.events 토픽
  4. ④ IdO HandoffEventConsumer 수신 → HANDOFF_ISSUED 처리
  5. ⑤ WebhookDispatcherService.insertOutbox() 기관별 호출
  6. ⑥ webhook_dispatch_outbox PENDING INSERT (ON CONFLICT DO NOTHING)
  7. ⑦ WebhookDispatchOutboxRelay 500ms 폴링
  8. ⑧ HTTPS POST → 기관 (HMAC-SHA256, 지수백오프)
  9. ⑨ 2xx → DISPATCHED / 실패 → 재시도

⚠️ 핵심 설계 포인트

  1. 멱등성 ON CONFLICT (source_event_id, agency_code) DO NOTHING
  2. PII 보호 Webhook payload에 qimUserId/CI 원본 포함 금지
  3. 지수백오프 2초 → 4초 → 8초 → … 최대 FAILED
  4. 기관 격리 각 기관별 독립 레코드 → 한 기관 장애가 타 기관에 영향 없음

🔵 프로비저닝 흐름

  1. ① Q-IM OutboxServiceImpl → Kafka qim.user.events USER_REGISTERED 발행
  2. ② IdO QimSpMemberEventConsumer 수신
  3. ③ ProvisioningServiceImpl — 기관 목록 조회, 최대 68건 INSERT
  4. ④ provisioning_outbox 기관별 1건 (ON CONFLICT DO NOTHING)
  5. ⑤ ProvisioningOutboxRelay 30초 폴링
  6. ⑥ 각 기관 HTTPS POST → COMPLETED 또는 백오프 재시도

⏱️ 백오프 전략

  1. 1회 실패 1분 후 재시도
  2. 2회 실패 5분 후 재시도
  3. 3회 실패 30분 후 재시도
  4. maxRetry 초과 DEAD_LETTER → 수동 복구 또는 알람
