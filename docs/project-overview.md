## 1. 이 프로젝트는 무엇인가

**Idem은 여러 기관(테넌트)의 회원가입과 로그인을 동일인 기준으로 하나로 통합하는 플랫폼입니다.** 첫 적용 사례인 OnePass(중기원패스)는 중소기업 지원 유관기관(최대 68개)을 대상으로 합니다.
이용자는 원패스 계정 하나로 여러 기관 서비스를 다시 가입하지 않고 이용하고, 기관은 회원관리·본인인증·보안을 플랫폼 표준에 맡길 수 있습니다.

핵심 가치는 세 가지입니다.

- **통합 로그인**: 한 번의 가입, 한 번의 로그인 — 기관마다 반복하던 가입·로그인을 원패스 계정 하나로 대체(SSO).
- **통합 회원**: 여러 기관에 흩어진 동일인 계정을 실명인증 기반으로 하나로 연결(골든 레코드).
- **연합 인가**: 기관 간 역할·권한 정보를 표준 방식(SCIM 2.0)으로 동기화.

## 2. 왜 필요한가 (해결하는 문제)

| 현재의 문제 | OnePass의 해법 |
|---|---|
| 기관마다 별도 가입·로그인 — 이용자가 수십 개 계정과 비밀번호를 관리 | 원패스 계정 하나로 참여 기관 전체 로그인 |
| 동일인이 기관마다 다른 계정으로 존재 — 지원 이력이 흩어지고 중복 지원 파악 곤란 | 실명인증(CI) 기반으로 동일인을 식별해 하나로 연결 |
| 기관마다 본인인증·보안을 자체 구축 — 중복 투자, 수준 편차 | 본인인증(NICE/OACX)·암호화·감사를 플랫폼이 표준 제공 |
| 기관 시스템 환경이 제각각(최신 ~ 20년 전 레거시) — 연동 자체가 난제 | 기관 상황별 연동 방식 제공(4종 + 레거시용 게이트웨이 계획) |

## 3. 주요 기능

### 3.1 통합 로그인 (SSO)

이용자가 원패스에서 로그인하면, **60초 동안만 유효한 1회용 암호화 티켓(Handoff)** 이 발급되어 기관 사이트로 전달됩니다. 기관은 이 티켓을 플랫폼에 검증 요청한 뒤 자체 세션을 만들어 이용자를 로그인시킵니다. 기관 세션은 기관이 소유하므로, **플랫폼에 장애가 나도 이미 로그인한 이용자는 계속 서비스를 이용할 수 있습니다**(장애 격리 설계).

### 3.2 본인인증과 인증 등급

NICE·OACX 연계 실명인증을 제공하며, 서비스 민감도에 따라 인증 등급(L1 간편 ~ L3 고보안)을 차등 적용합니다. 금융·국방 등 고보안 기관은 L3 + 최소 속성 전달로 대응합니다.

### 3.3 통합 회원 (동일인 식별)

실명인증에서 얻는 연계정보(CI)를 기준으로 동일인을 식별해 대표 계정(골든 레코드)을 만듭니다. 기관에는 실명정보 대신 **기관별로 다른 가명 ID(DI)** 만 전달해, 기관 간 이용자 추적을 차단하고 개인정보 노출을 최소화합니다. CI는 AES-256 암호화 저장, 접근은 KMS(Vault)로 통제합니다.

### 3.4 연합 인가 (권한 동기화)

"이 사람이 A기관에서 어떤 역할인가"를 관리하는 권한 원장(q-authz)을 두고, 국제 표준(SCIM 2.0 Groups)으로 기관과 역할을 동기화합니다. 권한 부여·회수는 이벤트로 각 기관에 전파되고, 기한부 권한은 만료 시 자동 회수됩니다.

### 3.5 기관 연동 채널

기관 개발 부담을 낮추기 위해 여러 연동 수단을 제공합니다.

- **Java SDK**(Java 8+, 의존성 0) — 티켓 검증·이벤트 연동을 몇 줄로 구현
- **웹훅**(서명 검증) 또는 **폴링** — 회원 변경·탈퇴 등 이벤트 수신(수신 서버가 없어도 폴링으로 가능)
- **프로비저닝** — 플랫폼의 회원 변경을 기관으로 자동 전달(멱등 처리)
- **크로스기관 SSO(CAST)** — A기관에 로그인한 이용자가 B기관으로 재로그인 없이 이동
- **레퍼런스 구현(agency-stub)** — 기관 개발자가 그대로 참고할 수 있는 동작하는 예제

## 4. 시스템 구성

Java 21 / Spring Boot 기반 마이크로서비스 구조이며, 컨테이너(Kubernetes/Helm)로 배포합니다.

| 구성요소 | 역할 |
|---|---|
| `q-sign` | 로그인·인증 게이트웨이 (Keycloak 연계, 소셜/간편 로그인) |
| `q-im` | 통합회원 원장 — 회원 데이터의 정본 (MariaDB) |
| `ido` | 기관 연동 오케스트레이터 — 티켓(Handoff)·본인인증·웹훅·프로비저닝 중계 |
| `q-authz` | 연합 인가 서비스 — 역할·권한 원장, SCIM 동기화 (PostgreSQL) |
| `onepass-fe` | 이용자 웹 화면 (React) |
| `onepass-agency-sdk` | 기관용 Java SDK (Java 8+) |
| `onepass-agent` | 기관 서버(WAS)에 설치하는 토큰 검증 에이전트 (JDK 8+ 환경) |
| `agency-stub` | 기관 연동 레퍼런스(예제) 서버 |
| `outbox-relay-batch` | 이벤트 중계 배치 — 데이터 변경을 유실 없이 전파(아웃박스 패턴) |

공통 인프라: MariaDB·PostgreSQL(데이터), Redis(세션), Kafka(이벤트), Vault(암호키 관리), Prometheus·Grafana·Loki(모니터링·알람).

## 5. 다양한 기관 환경, 어떻게 연동하나

참여 기관의 시스템은 최신 클라우드부터 20년 전 레거시(JDK 1.5, MiPlatform)까지 다양합니다. 기관 상황별로 연동 방식을 다르게 제공합니다.

| 기관 유형 | 연동 방식 |
|---|---|
| 표준 기관 (모던 Java, 개발 여력 있음) | **DIRECT** — SDK로 직접 연동 (즉시 가능, 파일럿 대상) |
| 자체 SSO 보유 기관 | **INTERNAL_SSO** — 기존 SSO를 대체하지 않고 공존. 회원 연결부터 시작 |
| 폐쇄망·고보안 기관 (금융·국방 등) | **BRIDGE** — 중계 서버 경유 + L3 고보안 인증 |
| 레거시 Apache 앞단 (전자정부프레임워크 등) | **APACHE_GATE** — 기존 Apache에 검증 모듈만 추가 |
| 레거시 스택 (JDK 1.5, MiPlatform 등) | **Edge Gateway(계획)** — 기관 시스템을 고치지 않고 앞단 게이트웨이가 인증을 대신 처리. 기관 실태조사 후 투자 결정 |
| 비-Java, 모바일 앱, 호스팅 임차형 | 표준 REST 명세(OpenAPI)·모바일 표준 플로우·호스팅 벤더 경유 (로드맵) |

> **원칙**: 기관 자체 로그인은 최소 1년 이상 병행 유지(플랫폼 장애 시 자연 우회로), 기관이 원치 않는 전환은 강제하지 않습니다.

## 6. 보안·개인정보 보호

- 실명 연계정보(CI)는 AES-256-GCM 암호화 저장, 암호키는 Vault(KMS)로 통제
- 기관에는 가명 ID(DI)만 전달 — 기관 간 이용자 추적 불가 구조
- 로그인 티켓은 60초 유효·1회 사용 후 폐기, 위·변조 방지 서명(HMAC) 적용
- 기관 간 데이터는 기관코드 단위로 격리(행 수준 보안, RLS)
- CI 파이프라인에 보안 취약점 스캔(OWASP·Trivy) 상시 적용, 전 구간 감사 로그

### 7.2 출시 경로

```text
① 운영 선결조건 충족 (Wave 0 게이트: 인프라 이중화·백업·키 관리 등 6항목)
        ↓
② 파일럿 출시 (협조 기관 소수)
        ↓
③ 하드닝 · 기관 실태조사 (68개 기관 환경 파악)
        ↓

```
