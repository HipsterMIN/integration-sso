## 0. 결론 요약 (Executive Summary)

1. **운영 성립성 — 조건부 미성립.** 앱 계층(HA·관측·보안 가드)은 수준급이나, **상태 계층(Redis SPOF·DB 백업/DR 0건·Vault 토큰 갱신 미구현)** 과 **회원 데이터 루프의 반쪽 구현**(§2.3)이 막는다. **파일럿은 "지금"이 아니라 Wave 0 게이트(§6.5 — 필수 6항목) 충족 시 가능**하며, 게이트 항목은 모두 실행 가능한 엔지니어링/운영 과제다.
2. **기관 다양성 — 절반은 이미 설계됨, 절반은 공백.** DIRECT/BRIDGE/APACHE_GATE/INTERNAL_SSO 4개 연동 패턴, 자체 SSO ADR, 고보안·폐쇄망·카오스 시나리오까지 **이미 인지·구현**(§3.1). 그러나 ⓐ **JDK≤7 레거시는 문서상 "✅지원"과 달리 3중 차단으로 연동 불가**, ⓑ **MiPlatform/Nexacro류 RIA는 저장소 언급 0건**, ⓒ **비-Java 무대응**, ⓓ **모바일 앱·SaaS 임차형·공유시스템 축 자체가 부재**, ⓔ **68개 기관 실명 인벤토리 부재**(§3.2~3.3).
3. **전략 전환 — "에이전트가 레거시를 해결한다"는 가정을 폐기**하고, 레거시·RIA·비Java를 해소하는 **기관 전면 Edge Gateway 패턴을 신설**한다(§5.3). 단, 검증 결과를 반영해 **게이트웨이는 "기관의 새 SPOF·새 운영 부담·새 개인정보 경유지"가 될 수 있다는 긴장을 정면으로 다룬다** — 가용성 설계·운영 RACI·보안 경계·법적 지위·MiPlatform 성립 조건을 §5.3에 명문화했고, 상당수는 **기관 실측 전에는 가설**이다.
4. **실행은 Track 0(기관 실태조사)이 모든 것에 선행한다.** 유형 비율(40/25/20/15%)은 추정치다. **Edge Gateway는 Track 0 판독 전 PoC 설계 문서 이상 착수 금지**(§6.7).
5. **채택(참여)이 기술만큼 큰 실존 리스크다.** 기관 니즈 N1~N7은 전부 방어적(손실 회피)이며, "왜 참여해야 하는가"의 효익 논거가 없으면 자발적 연합 모델은 지연된다 — §5.6(효익·비용 모델)과 §7 의사결정 #12로 승격했다.

## 2. Part I — 통합회원 서비스 운영 성립성 진단

### 2.1 "중앙 장애 = 전 기관 로그인 장애"인가? — **아니다 (단, 신규 원패스 로그인은 맞다)**

| 시나리오 | 실제 동작 | 근거 |
|---|---|---|
| **기존 기관 세션** | **유지** — AGSID 검증은 기관 로컬 DB만 조회(idle 30분/절대 8h), OnePass 무호출 | `AgencySessionService.java:159-186` |
| 기관 **자체 로그인** | 영향 없음 — 옵션 A "완전 분리"가 기본 권장("원패스는 기관 SSO를 대체하지 않음") | `sso-agency-integration-guide.md` §2.1 |
| **신규 원패스 로그인** | 실패 — verify Retry 3회→CB OPEN→기관은 503 "잠시 후 재시도" 안내 | `IdoVerifyClient.java:73-143` |
| 에이전트 구간 | fail-open — 검증 실패 시 요청 통과. **단, 문서상 설계이며 실연동 미검증(§3.2 G-D)** | `onepass-agent-architecture.md:726-748` |
| **Edge Gateway 채택 기관(§5.3)** | ⚠️ **게이트웨이는 기관 전 트래픽 경유 지점 — 게이트웨이 장애 = 해당 기관 서비스 전체 장애 가능.** 폭발 반경 한정 원칙의 예외가 되므로 §5.3.2 가용성 설계(이중화+bypass 스위치)를 필수 요건으로 한다 | 본 문서 §5.3.2 |
| **미구현 완충** | `agency_meta.fallback_login_url` 컬럼 존재·**참조 코드 0건** — 장애 시 기관 임시 로그인 리다이렉트 미착수 | `V4__add_qim_sp_receiver.sql:114-118` |

**전환기 4원칙(온보딩 표준 요건으로 명문화)**: ① 기관 자체 로그인 **최소 1년 이상 병행 유지**(중앙 장애의 자연 우회로) ② `fallback_login_url` 구현 P1 승격 ③ 기관 세션 독립성(로컬 세션 수명 동안 OnePass 무의존) ④ Edge Gateway 채택 기관은 **게이트웨이 bypass 스위치**(게이트웨이 우회 시 기관 자체 로그인만으로 운영 가능) 확보.

### 2.3 회원 데이터 루프의 실제 완결성 — **현재 반쪽**

```text
[플랫폼→기관]  프로비저닝: 구현됐으나 기본 OFF(2중 플래그+dry-run) ─── 🟡 스위치만 켜면 됨
               페이로드 identity_hash: 자기참조 해시 — 기관 원장 매칭 신호 가치 0 ─ ❌ 재설계
               MEMBER_WITHDRAWN: 프로비저닝 트리거 제외, "별도 처리" 경로 완결성 미확인 ─ ❌
[기관→플랫폼]  gateway inbound: 수신·감사·멱등까지 되고 라우팅이 log-only ──── ❌ 원장 미반영
[식별 연속성]  DI = HMAC(agency:qimUserId) → 계정 병합 시 DI 변경 — 통지/재설계 미결 ─ ❌
[법적 근거]    기관 간 연계 동의(전환동의 vs 일괄통합동의) 미결 ────────────── ❌ 의사결정
```

> **함의**: "운영 환경이 되는가"의 대답은 인프라(§2.2)만이 아니라 **이 루프의 완결**에 달려 있다. `identity_hash` 재설계와 인바운드 라우팅 구현은 회원통합 마스터 플랜 Phase 3의 선행 조건이다. (마스터 플랜 격차 목록에 G8=인바운드 log-only, G9=identity_hash 신호가치 0으로 추가 등재 — README 참조)

### 2.4 안정 운영 성립을 위한 최소 조건 (10)

1. **Redis HA**(Sentinel/Cluster) + 세션 소실·rate-limit fail-open 정책 재정의
2. **DB 백업·PITR·복구 리허설 + RPO/RTO 문서** + PostgreSQL/MariaDB HA 확정
3. **Vault 토큰 자동 갱신(F5.3)** + Vault HA
4. 스케줄러 단일화(q-authz ShedLock, q-im 인프로세스 릴레이 disable 플래그 → relay-batch 일원화)
5. redis/kafka/pg **exporter 스크레이프 + 인프라 알람 부활**
6. **실 인프라 부하테스트**(60k 동시 인증, 68기관 프로비저닝, 재시도 폭주)
7. SLA 문서 제정(기관 지원 SLA 포함) + 인시던트 프로세스 명문화
8. 기관 실데이터 온보딩 + Key 회전 자동화 + **기관 셀프서비스 포털/지원 데스크**(연동 상태 대시보드·Key 셀프서비스·샌드박스 테스트 콘솔·티켓)
9. 프로비저닝/웹훅 per-agency circuit breaker(수동 비활성 대체)
10. `fallback_login_url` 구현 + DR 훈련 절차

### 2.5 GO/NO-GO(2026-06-30) 대비 판정 변경점

본 문서는 선행 GO/NO-GO 평가를 다음과 같이 **일부 상향·보강**한다(정본은 본 문서):

| 항목 | GO/NO-GO 분류 | 본 문서 | 사유 |
|---|---|---|---|
| Vault F5.3 | C(단계적 하드닝) | **파일럿 게이트의 완화 허용 항목**(§6.5 — 수동 갱신 런북 전제) | 파일럿 중 TTL 만료 = 전 Handoff 차단(S-D3). 완전 자동화는 전면 운영 전 필수 |
| DB 백업/DR | 미등재 | **신규 블로커**(A-2) | 실사에서 백업·복구 자산 0건 확인 — 회원 데이터를 다루는 서비스의 최소선 |
| 스케줄러 중복 | 미등재 | **신규 블로커**(A-4) | replica 3 배포값과 단일리더 가정의 명시적 모순 |
| Redis SPOF | "인프라 준비" 일반 항목 | **최대 단일장애점으로 구체화**(A-1) | readiness 연동·세션 전멸·rate-limit fail-open 삼중 결합 |
| "파일럿 수주 내 현실적" | 문구 유지 | **Wave 0 게이트 충족 시**로 조건화(§6.5) | 공수 추정 없는 낙관 문구 정정 |

| 레거시 Apache 앞단(eGovFrame) | `APACHE_GATE` — mod_auth_openidc 호환 헤더 사전 Push — **전략 구현** | `ApacheGateHandoffStrategy.java:107-116` |

| 고보안 L3(금융위·국방부급) | `min_auth_level=L3` + 최소 속성 — **구현** | V13 `AGENCY_STRICT_L3` |
| 장애·악의 기관 | 카오스 시나리오 + CB/Retry — **테스트 존재** | V13 `AGENCY_CHAOS_001` |

유형 분포 추정(wiki/guide/06): 독립 계정 ~40% / 자체 OIDC ~25% / SAML ~20% / 상용 SSO ~15% — **추정치이며 실측 아님**.

## 4. onepass-agent 재정의 (정직성 회복)

1. **즉시(C-1)**: 기관용 가이드의 JEUS 4/5/6·JDK≤7 "✅ 지원" 표기를 "미지원(로드 불가 — D-AGENT-01)"으로 정정. 지원 매트릭스를 **실검증 완료(테스트베드 7종) / 전략 존재·미검증 / 미지원** 3단계로 재분류. *(본 커밋에서 1차 정정 수행)*
2. **역할 축소 재정의**: 에이전트 = *"JDK 8+ Servlet WAS에서, 이미 발급된 토큰의 사후 검증 게이트"*. SSO 로그인 UX는 에이전트 담당이 아님을 명시.
3. **수리 대상(유지 시)**: verify 엔드포인트 서버측 구현+경로 통일 / 레거시 전략 no-op 버그 / fail-closed 옵션(D-AGENT-02) / 테스트베드 실구동.
4. **JDK≤7 direct 지원은 추진하지 않는다.** §5.3 Edge Gateway가 동일 문제를 기관 JVM 밖에서 해소하며, Edge Gateway가 NO-GO일 경우의 S5 폴백은 §5.3.8에 독립 시나리오로 정의한다.

### 5.1 S1 표준 기관 — 즉시 실행 가능

기존 자산으로 충분(DIRECT+SDK+Handoff/전환/웹훅·폴링). 파일럿 웨이브 대상. 준비물은 Wave 0 게이트(§6.5)와 온보딩 킷 표준화.

### 5.2 S2 자체 SSO 보유 기관 — "대체가 아니라 공존"

1. **기본 = 옵션 A(완전 분리·공존)**: 기관 SSO 유지, OnePass는 추가 수단. 회원연계(전환)만 먼저. 현재 구현으로 가능.
2. **옵션 B(위임)**: OnePass 인증 후 기관 SSO 세션 수립(`INTERNAL_SSO` 전략). ⚠️ **기관 SSO 측 수신 모듈 개발이 필요하며 상용 제품(드림시큐리티 등)은 벤더 과업** — 기관별 개별 발주 대신 **플랫폼이 주요 벤더와 표준 연동 모듈을 공동 개발·인증해 전 기관 재사용**(Track D-4)하고, 커스터마이징 비용 분담은 §7-#8에서 결정.
3. **옵션 C(브로커링)**: Keycloak Identity Brokering(ADR-2026-004). **SAML SP(DEBT-02) 구현 선행.**
4. **계정 연결이 SSO 통합보다 먼저다**: CI 기반 전환으로 `기관 mbrId ↔ qimUserId` 매핑을 먼저 축적 — SSO 방식 결정과 무관하게 통합회원 가치 성립.
5. **이중 로그인 전환기**: 소멸 일정은 기관 자율, 플랫폼 강제 없음.

### 5.3 S5 레거시 기관 — OnePass Edge Gateway (신설 제안, v0.2 전면 보강)

**문제의 재정의**: JDK 1.5+MiPlatform 기관의 제약 ①구형 JVM ②TLS 1.0 ③RIA(리다이렉트 불가) ④개발 여력 부족은 기관 애플리케이션 "안"에서 해결이 원천 불가 → "밖"(전면 게이트웨이)에서 해결한다.

#### 5.3.1 기본 구조

```text
[사용자 브라우저/MiPlatform 클라이언트]
        ▼ (기관 접점 — HTTPS 의무화 여부는 §7-#9 결정)
┌────────────────────────────────────────────────────┐
│ OnePass Edge Gateway (기관 DMZ, 플랫폼 표준 배포물)      │
│ · 플랫폼과는 TLS1.2+ 종단 / 미인증 브라우저 → 로그인 리다이렉트│
│ · Handoff verify → 게이트웨이 세션 발급                  │
│ · 레거시 WAS로 X-Remote-User/X-Auth-Level 주입          │
│ · RIA 트래픽: 세션 쿠키/일회성 토큰(§5.3.4)로 통과 판정      │
└──────────────┬─────────────────────────────────────┘
               ▼ (내부 HTTP + §5.3.6 보안 경계)
 [기관 레거시 WAS — JEUS 4/5, JDK 1.5 등: §5.3.5 최소 수정]
```

**기존 자산과의 정합**: `APACHE_GATE` 전략(게이트웨이 검증+헤더 신원 전달)의 **제품화**다. S4 기관은 **"Apache 플레이버"(기존 Apache에 검증 모듈만 추가 — 이중 프록시 회피)** 를 기본으로 하고, 신규 설치(체이닝/대체)는 예외 토폴로지로 둔다.

#### 5.3.2 가용성 설계 — "게이트웨이가 기관의 새 SPOF"라는 긴장의 정면 처리

- 게이트웨이는 기관 **전 트래픽** 경유 지점 → **게이트웨이 장애 = 기관 서비스 전체 장애 가능**(§2.1 표에 명시). 따라서:
  - **active-passive 2대(keepalived/VRRP) 표준 구성** 또는 기관 L4 뒤 배치를 설치 표준으로 한다.
  - **bypass 스위치 필수**: 게이트웨이 우회 시 기관 자체 로그인만으로 서비스가 계속 돌아가는 구성(§2.1 4원칙-④)을 설치 체크리스트에 포함.
  - **세션 저장 방식 명시**: 인메모리 세션이면 failover 시 전 사용자 재로그인 — 기본은 "짧은 세션 + 재로그인 허용", 대규모 기관은 로컬 KV 복제 옵션. 설치 시 선택·문서화.

#### 5.3.3 운영 모델(RACI) — "남의 장비를 우리 DMZ에" 문제

| 활동 | 기본 모델 (기관 소유·기관 운영) | 위탁 모델 (§7-#8 결정) |
|---|---|---|
| 설치 | 기관(플랫폼 설치 지원) | 플랫폼 파견 |
| 패치/CVE | **서명된 오프라인 패키지를 플랫폼이 배포 → 기관이 적용**(DMZ 원격 접근 불가 전제). 선택적 자동 업데이트 옵트인 | 플랫폼(기관 서면 승인 기반) |
| 모니터링 | 기관(게이트웨이가 표준 메트릭 노출) + 플랫폼 헬스 원격 관측(아웃바운드 하트비트) | 플랫폼 |
| 장애 1차/2차 | 기관 1차 / 플랫폼 2차(지원 SLA) | 플랫폼 |
| 책임/면책 | **기관 협약서 템플릿에 게이트웨이 전용 조항**(플랫폼=배포물 제공자, 기관=운영 주체) 포함 | 위탁 계약 체결(SLA·손해배상 한도 명시) |

> **핵심 긴장**: 기본 모델(기관 소유·운영)은 "기관 개발 여력 부재"라는 전제와 충돌한다 — 운영 여력조차 없는 기관에 게이트웨이 운영을 지우면 채택이 막힌다. 그래서 위탁 모델을 **동급 옵션**으로 두되, 위탁은 "플랫폼이 기관 DMZ 장비를 원격 운영"하는 것이므로 **망분리·개인정보 위탁 계약·접근통제**가 선결(§5.3.6·§5.3.7). 어느 모델이 다수가 될지는 Track 0의 "기관 운영 여력" 항목으로 실측한다.

#### 5.3.4 RIA(MiPlatform/Nexacro) 성립 조건 — **검증 전 가설**

MiPlatform/Nexacro/X-Internet는 브라우저 위 런타임이므로 "리다이렉트 기반 로그인"이 불가하다. Edge Gateway가 이를 흡수하려면 다음이 성립해야 하며, **전부 기관 실물 대상 PoC로 검증하기 전에는 가설이다**:

| 가설 | 성립 조건 | 검증 방법(Track 0/PoC) |
|---|---|---|
| H1. 최초 진입은 HTML 셸 | RIA 로딩 전 브라우저가 게이트웨이 HTML을 거침 → 여기서 로그인 리다이렉트 수행 | 기관 실제 진입 URL의 초기 응답이 HTML인지 확인 |
| H2. 런타임 요청이 세션 쿠키 동반 | MiPlatform HTTP 통신이 브라우저 쿠키 자를 공유 → 게이트웨이가 쿠키로 인증 판정 | **미검증 — MiPlatform 통신 채널의 쿠키 전파 여부는 제품/버전별 상이**. 실트래픽 캡처 필수 |
| H3. 인증 실패의 앱 인지 | 401/302를 RIA가 처리 가능(아니면 흰 화면) | 기관 화면단 커스터마이징 범위 확인 → §5.3.5 최소 수정에 포함 |

> H2가 깨지면(쿠키 미동반) 게이트웨이 단독 해결 불가 → 기관 RIA 통신 초기화 코드에 토큰 헤더 주입이라는 **기관측 수정**이 필요(=완전 무개발 불성립). **MiPlatform 지원은 "채널 성립 시"라는 조건부로만 표기**하고, Track 0 PoC 이전에는 "지원"이라 광고하지 않는다.

#### 5.3.5 "최소 수정" 정직 고지 — **"완전 무개발"은 과장**

게이트웨이는 기관 애플리케이션 코드 변경을 **최소화**하지만 0으로 만들지 못한다. 정직한 범위:

- **인프라 변경(필수)**: DNS/L4가 게이트웨이를 경유하도록 전환, 게이트웨이 2대 설치, 방화벽 규칙, 인증서 발급.
- **앱 변경(대개 필요)**: ⓐ 신원 소비 — 기존 로그인 화면을 게이트웨이 주입 헤더(`X-Remote-User`) 신뢰로 대체하는 소량 수정 ⓑ 로그아웃 연동 ⓒ RIA는 §5.3.4-H3.
- **무개발이 가능한 경우**: 이미 `REMOTE_USER`/컨테이너 인증 헤더를 소비하는 eGovFrame·Apache 앞단 기관(S4)에 한정.

> 온보딩 킷·영업 자료의 "무개발 연동" 문구를 **"인프라 전환 + 신원 소비부 최소 수정"** 으로 정정한다(문서 신뢰성 = N7·채택의 전제).

#### 5.3.6 보안 경계 — 내부 HTTP 헤더 신원 주입의 위험

게이트웨이→WAS 구간은 `X-Remote-User`로 신원을 전달하므로, **이 헤더를 위조한 요청이 WAS에 직접 도달하면 인증 우회**가 된다. 설치 표준:

1. **WAS는 게이트웨이 경유 트래픽만 수신**(바인딩 주소 제한/방화벽/mTLS 중 택1 필수). 게이트웨이 우회 직접 접근 차단.
2. 게이트웨이는 인바운드 `X-Remote-*` 헤더를 **무조건 제거 후 재주입**(클라이언트 위조분 스트립).
3. 내부 구간 평문 HTTP 허용 여부는 기관 망 등급별 결정 — L3/폐쇄망은 내부도 mTLS 의무.
4. 게이트웨이 세션 토큰은 게이트웨이 서명, WAS는 헤더만 신뢰(토큰 재검증 불요) — 단 1·2가 전제.

#### 5.3.7 개인정보 경유지(PIPA) 문제 — 게이트웨이는 새 위수탁 지점

게이트웨이는 로그인 신원·세션을 **취급·매개**하므로 개인정보 처리 흐름에 새 노드가 생긴다:

- **위탁 모델**: 플랫폼이 기관 개인정보를 위탁처리 → **개인정보 처리위탁 계약·수탁자 안전조치 고지 의무**(개인정보보호법 §26). 협약서 템플릿에 반영.
- **로그 최소화**: 게이트웨이는 신원 식별자·세션을 **로깅하지 않음(감사 최소필드만)** 기본값. 평문 개인정보 미저장.
- **전송·저장 암호화**: 세션 저장(§5.3.2)·내부 구간(§5.3.6) 암호화 등급을 기관 개인정보 영향평가(PIA) 대상으로 명시.
- **국외/제3자 이슈 없음**: 게이트웨이는 기관 DMZ 내부 배치 → 개인정보 국외이전 아님(플랫폼 SaaS 위탁 모델일 때만 재검토).

#### 5.3.8 Edge Gateway NO-GO 시 S5 폴백 (독립 시나리오)

Track 0/PoC에서 Edge Gateway가 성립 불가·투자 부적합으로 판정되면(예: MiPlatform H2 다수 실패, 기관 DMZ 정책 불허), S5는 다음 순서로 폴백한다:

1. **회원연계만 우선(로그인 통합 보류)**: CI 기반 전환(채널 #3)으로 `기관 mbrId ↔ qimUserId` 매핑만 축적 → 통합회원 가치는 확보, SSO는 기관 리뉴얼 시점까지 유예.
2. **기관 리뉴얼 연계**: 레거시 WAS 교체(대개 3~5년 주기 정보화 사업) 시 S1 경로로 자연 편입 — 강제 대신 대기.
3. **배치/폴링 프로비저닝**: 실시간 SSO 대신 `GET /api/v1/agency/events` 폴링(채널 #5 대체 pull)으로 회원 동기화 — 개발 여력 최소 기관용.

> 즉 **S5는 Edge Gateway 성패와 무관하게 "회원연계"라는 하한선을 갖는다.** Edge Gateway는 로그인 통합의 상한을 올리는 투자이지, S5 참여의 전제조건이 아니다.

### 5.4 S6 비-Java 스택 — OpenAPI 우선

1. **REST OpenAPI 3.0 명세 정본화**: Handoff verify/전환/폴링/게이트웨이 인바운드의 언어중립 스펙 공개 → .NET/PHP/Node/Python 자가연동 가능.
2. **Edge Gateway 재사용**: 개발 여력 없는 비-Java 기관은 §5.3 게이트웨이가 스택 무관하게 흡수(게이트웨이가 헤더 주입 → WAS는 헤더만 읽음).
3. **레퍼런스 최소화**: 언어별 풀 SDK 대신 "명세 + 서명·검증 스니펫 3종(HMAC/Ed25519/HS256)" 제공. 유지보수 부담 통제.

### 5.5 onepass-agent 경로 — §4로 이관

에이전트 수리/축소는 §4에 통합. S5의 로그인 통합은 에이전트가 아니라 §5.3 Edge Gateway가 담당(에이전트는 JDK 8+ 사후검증 게이트로 역할 축소).

### 5.6 효익·비용 모델 (N8 — v0.2 신설, 채택 리스크 대응)

기관 니즈 N1~N7은 전부 **방어적(손실 회피)** 이다. 자발적 참여를 만들려면 효익이 비용을 넘어야 한다.

**기관이 지는 비용(정직한 집계)**

| 세그먼트 | 초기 비용 | 운영 비용 |
|---|---|---|
| S1 모던 Java | SDK 통합 소규모 개발 | 낮음(라이브러리 업글) |
| S2 자체 SSO | 연계/브로커링 개발 or 벤더 발주 | 중간 |
| S5 레거시(게이트웨이) | 게이트웨이 2대 인프라 + 신원소비 수정 + 망/보안 검토 | **중간~높음(게이트웨이 운영·패치)** |

**기관이 얻는 효익(가설 — Track 0 인터뷰로 검증·계량)**

- **회원 확보**: 원패스 이용자의 신규 유입(전환 유도) — 기관 관점 최대 유인. 계량 지표: 전환 유입 수/월.
- **본인인증 비용 절감**: NICE/OACX 재계약·건당 비용을 플랫폼 공동구매로 대체 가능 여부(§7-#12 검토).
- **로그인 UX·보안 수준 상향**: 자체 구축 대비 L2/L3 인증·감사·이상탐지 이관.
- **규제 대응 이관**: 인증·개인정보 안전조치 일부를 플랫폼 표준으로 흡수.

**채택 촉진 레버(정책·비기술)**

1. **의무화 vs 자율**: 공공 통합인증이 상위 지침으로 **의무**면 효익 논거 부담이 준다 — 소관부처 정책 결정(§7-#12).
2. **비용 분담**: 게이트웨이 하드웨어·구축비를 사업 예산으로 **중앙 부담**(기관 부담 0 구축)하면 S5 채택 급상승 — 예산 확보가 관건.
3. **단계 인센티브**: 파일럿 참여 기관 우선지원·레퍼런스 인정.

> **결론**: 효익이 방어적 니즈뿐이면 자발적 연합은 지연된다. **의무화 수준·중앙 예산 부담**이라는 두 정책 레버가 기술만큼 채택을 좌우한다 → §7-#12 최우선 의사결정으로 승격, §8 최상위 리스크로 등재.

### 5.7 공공 보안 인증(KCMVP·보안적합성) 갭 — N6 심화

공공기관 도입은 암호모듈·보안적합성 검증을 요구할 수 있다. 현 저장소 기준 갭:

| 항목 | 현황 | 갭·조치 |
|---|---|---|
| **암호모듈(KCMVP)** | Ed25519·AES-GCM·HMAC 등 표준 알고리즘 사용, 그러나 **검증필 암호모듈 사용 여부 미확인** | 공공 도입 대상 구간(본인인증·서명)은 KCMVP 검증모듈 사용 필요 가능 → 대상 식별·교체 계획 |
| **Ed25519 수용성** | CAST에 사용 | 공공 표준(전자서명/SEED/ARIA/국산) 대비 수용 여부 확인 — 미수용 시 대체 서명 |
| **보안적합성 검증(CC/보안기능확인서)** | 미착수 | 게이트웨이·SDK가 도입 대상이면 확인서 필요 여부 사전 확인 |
| **망분리·CSAP** | BRIDGE/L3 전략 有 | 클라우드 배포 시 CSAP 인증 필요 여부(민간/공공 클라우드 등급) |

> 이는 **파일럿 범위(제한 기관)에서는 유예 가능**하나, 68기관 전면·고보안 기관 확대의 **선결**이다. Track 0에서 대상 기관의 보안 요구 등급을 실측한다.

3. **Wave 2**: S2 옵션 B/C(브로커링·SAML) + S5 Edge Gateway(게이트 통과 시).
4. **Wave 3**: S6/S7 + 전면 확대(회원루프·보안인증 완결 전제).

### 6.5 Wave 0 게이트 — 파일럿 개시 필수 6항목

파일럿은 "지금"이 아니라 아래 **전부** 충족 시 개시한다:

1. **Redis HA** 구성(세션·jti·rate-limit 단일점 해소) 또는 파일럿 한정 축소범위+세션소실 수용 정책 문서화.
2. **DB 백업/PITR + 복구 리허설 1회**(RPO/RTO 문서) — 회원 데이터 서비스의 최소선.
3. **Vault 토큰 갱신** — 자동화 or **수동 갱신 런북+만료 알람**(파일럿 한정 완화 허용, §2.5).
4. **스케줄러 단일화**(중복 폴링/스캔 제거) 검증.
5. **시크릿·기관데이터 적재**(GO/NO-GO 체크리스트 B) + prod fail-fast 통과.
6. **CD 방식 확정**(KUBE_CONFIG or GitOps) + 롤백 절차 1회 리허설.

> 5·6은 GO/NO-GO 문서의 B/A4 항목과 동일 — 본 게이트가 그 실행 관문이다.

### 6.6 KPI·측정

- 운영: 인증 성공률/지연(p95), Redis/DB 가용성, DR 복구시간 실측(RTO), 스케줄러 중복 0.
- 채택: 온보딩 기관 수, 전환 유입 수/월(효익 지표, §5.6), 지원 티켓 SLA 준수율.
- 데이터 루프: 인바운드 원장반영률, identity_hash 재설계 후 매칭 정확도.

### 6.7 Track 0 게이트 (Edge Gateway 대형 투자 방지)

**Edge Gateway는 PoC 설계 문서 이상(코드/제품화) 착수를 다음까지 금지한다:**

1. Track 0에서 S5(레거시)·S6(비Java)·S8(호스팅) **실규모 확인** — 소수면 §5.3.8 폴백이 비용효율적일 수 있음.
2. MiPlatform **H2(쿠키 전파) 실트래픽 검증**(§5.3.4) — 실패 다수면 게이트웨이 단독 해결 불가.
3. 대상 기관의 **DMZ 장비 반입·위탁운영 정책 수용성** 확인(§5.3.3/§5.3.7).
4. 위 3건 통과 후 **PoC(기관 1곳 실물)** → 성립 시 제품화 예산 편성.

## 9. 요약 — 두 질문에 대한 답

**Q1. 통합회원 서비스가 진짜 안정적으로 운영될 수 있는가?**
> 앱 계층은 준비됐고 **상태 계층(Track A)과 회원 루프(Track B)를 완결하면 파일럿은 성립**한다. "지금"은 아니고 **Wave 0 게이트(§6.5) 충족 시**다. 게이트 항목은 전부 표준 기술로 실행 가능한 과제이지 미지의 연구가 아니다.

**Q2. 이기종 기관 니즈를 어떻게 해소하는가?**
> **세그먼트별 분기**: S1 즉시(기존 자산) · S2 공존 우선(연계 먼저) · S5 레거시는 **Edge Gateway(조건부 투자, Track 0 게이트 통과 시)** 로 기관 JVM 밖에서 해소하되 **회원연계 하한선(§5.3.8)** 을 항상 보장 · S6 OpenAPI · S7 모바일 표준플로우. 단 **가장 큰 변수는 기술이 아니라 "참여를 만드는 정책 레버(의무화·중앙예산)"**(§5.6/§8-R1)이며, 이는 소관부처 의사결정(§7-#12)에 달렸다.

> **다음 행동**: ① Track 0 실태조사 즉시 착수(무비용·선행) ② Track A/B 병렬 ③ Edge Gateway는 §6.7 게이트 전까지 PoC 설계 문서까지만. **본 커밋에서 §4-C-1(onepass-agent 지원표기 정정)을 함께 수행한다.**
