## 1. 왜 지금 결정이 필요한가

### 1.1 두 가지 길

현재 프로젝트는 분기점에 있다.

**길 A — 현재 방식 유지**
- 각 팀이 시연용 코드를 계속 발전시킨다
- 시연은 통과하지만, 운영 전환 시점에 전면 재개발이 필요하다
- 보안 우회 코드가 운영 환경에 진입할 위험이 있다

**길 B — integration-sso 채택**
- 이미 만들어진 정식 구현체를 기준으로 삼는다
- 각 팀은 담당 영역만 이어서 개발한다
- 운영 전환까지 추가 Sprint만 진행하면 된다

**지금 결정하지 않으면**: 각 팀이 서로 다른 방향으로 더 깊이 개발해 나가고, 이후 통합 비용이 기하급수적으로 증가한다.

### 1.2 현재 상황의 실제 모습

각 팀이 현재 진행하는 시연용 개발 방식에는 다음이 포함되어 있다:

- **암호화 검증 비활성화**: 실제 운영에서는 반드시 켜야 하지만, 시연용으로 꺼둔 상태
- **보안 파라미터 우회**: CSRF 방어(state 검증)가 꺼진 채 동작
- **데이터 미저장**: 사용자 추적·감사에 필요한 정보가 저장되지 않음
- **설계서 미준수**: 통합인증 설계서가 요구하는 구조와 다른 방식으로 구현

이 코드는 **시연 통과용**으로 만들어진 것이다. 운영 코드가 아니다.

---

## 2. integration-sso가 이미 해결한 것

### 2.1 구현 완료된 핵심 기능

`integration-sso` 프로젝트는 통합인증 설계서의 요구사항을 실제 동작하는 코드로 구현했다.

**인증 흐름 전체**
- 카카오·네이버·PASS·금융인증서·GPKI 등 다양한 인증 수단을 단일 인터페이스로 처리
- 사용자가 어떤 인증 수단을 써도 기관은 동일한 방식으로 사용자 정보를 수령

**기관 연동 표준화**
- N개 기관 시스템이 OnePass 하나를 통해 인증을 위임
- 기관이 추가되어도 핵심 시스템(Q-IM) 변경 불필요

**보안 체계 완비**
- 암호화, 서명 검증, 접근 제어, 개인정보 보호가 설계에 내재화
- 보안을 나중에 추가하는 것이 아니라 처음부터 적용

### 2.2 규모로 본 개발 성과

| 지표 | 수치 | 의미 |
|------|------|------|
| 완료 Sprint | 10개 | v1.0에서 v2.3.0까지 전 단계 완료 |
| 자동화 테스트 | 397개 통과 | 핵심 로직 검증 완료 |
| 빌드 성공 | 전 모듈 | 당장 기동 가능한 상태 |
| 인프라 구성 | Docker 완비 | 로컬 개발 환경 즉시 구성 가능 |
| 문서 | 일체 완비 | 아키텍처·API·개발 가이드 포함 |

## 3. 현재 방식의 위험과 비용

### 3.1 보안 위험

현재 시연용 코드에 포함된 보안 우회 항목들은 운영 전환 시 반드시 제거해야 한다. 제거 후 시스템이 제대로 동작하려면 설계서 기준의 구현이 필요하다. 이것이 곧 `integration-sso`가 구현한 내용이다.

> **결론**: 현재 방식을 계속하면 결국 같은 결과물을 다시 만들어야 한다.

### 3.2 일정 위험

| 시점 | 현재 방식 유지 시 | integration-sso 채택 시 |
|------|-----------------|------------------------|
| 3개월 후 | 팀별 코드 충돌 발생 | 기관 어댑터 완성 단계 |
| 6개월 후 | 통합 작업 착수 | 운영 전환 준비 완료 |
| 운영 전환 | 전면 재개발 필요 | 후속 Sprint 완료 후 전환 |

### 3.3 규정 준수 위험

보안 우회 상태의 시스템이 운영에 진입할 경우:
- 개인정보보호법 위반 가능성 (암호화 미적용 상태에서의 CI 처리)
- 정보보안 감사 불합격 (감사 로그 공백, 접근 제어 미비)

## 4. 채택 결정 시 달라지는 것

### 4.1 각 팀의 역할

| 팀 | 현재 상황 | 채택 후 |
|----|----------|--------|
| 인증 팀 | 인증 코어를 독자 개발 중 | integration-sso 기반으로 담당 모듈만 완성 |
| 기관 연동 팀 | 기관별 개별 인터페이스 개발 | 표준 어댑터 방식으로 기관 추가 |
| 인프라 팀 | 각 팀 환경 별도 관리 | 단일 Docker Compose 기반으로 통합 |
| 보안 팀 | 사후 보안 검토 필요 | 설계 내재 보안 기반 운영 검토 |

### 4.2 즉시 확보되는 자산

채택 결정 즉시 사용할 수 있는 것:
- 전체 인증 흐름 구현 코드
- 기관 연동 표준 (Handoff Ticket 메커니즘)
- 운영 인프라 구성 (Docker Compose)
- 모니터링 스택 (Prometheus + Grafana)
- 개발 가이드 및 API 명세 문서 일체

## 5. 권고 결정 사항

### 5.1 채택 결정

> **`integration-sso` 프로젝트를 통합인증 시스템의 정식 개발 기준으로 채택한다.**

### 5.2 채택 후 즉시 실행 사항

| 순서 | 내용 | 완료 기준 |
|------|------|---------|
| 1 | 전 팀 integration-sso 기반 개발 환경 구성 | 로컬 기동 확인 |
| 2 | 기관 연동 어댑터 개발 착수 (IdO → SMEP 등) | 어댑터 인터페이스 확정 |
| 3 | Q-IM 팀과 암호화 방식 협의 | encCi 알고리즘·키 정책 확정 |
| 4 | 운영 환경 보안 키 교체 계획 수립 | 교체 일정 확정 |

### 5.3 현재 시연 코드 처리

시연 완료 이후 각 팀의 임시 구현 코드는 **폐기**한다.  
`integration-sso`의 기관 시뮬레이터(`agency-stub`)가 시연 환경을 대체한다.
