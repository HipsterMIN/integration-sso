## 1. 우리 기관이 해당되는지 확인

다음 항목에 해당하는 기관이 이 가이드의 대상입니다.

| 확인 항목 | 해당 | 해당 없음 |
|----------|------|---------|
| 기관 자체 로그인 시스템(SSO, IAM, LDAP 등)을 운영 중 | ✅ | |
| 직원/사용자가 기관 아이디/비밀번호로 별도 로그인 | ✅ | |
| 원패스(공공 통합인증)와 기관 로그인을 병행 운영 예정 | ✅ | |
| 기관 SSO와 원패스를 "연결"하거나 "통합"하라는 지시를 받음 | ✅ | |

**해당 없는 경우**: 기관 자체 SSO 없이 원패스만 사용할 예정이라면, 일반 연동 가이드를 참고하세요.

## 2. 원패스 연동의 의미 — 기관 SSO와 무엇이 다른가

### 2.1 원패스는 기관 SSO를 "대체"하지 않습니다

흔한 오해입니다. 원패스는 기관 내부 SSO와 경쟁하거나 대체하는 시스템이 아닙니다.

```
[오해] 원패스 → 기관 SSO 폐지 → 원패스로 단일 통합
[실제] 원패스 + 기관 SSO 공존 → 원패스가 "외부 인증 경로" 추가
```

### 2.2 원패스가 하는 일

| 원패스 담당 | 기관 SSO 담당 |
|------------|-------------|
| 공공기관 간 통합 인증 | 기관 내부 사용자 인증 |
| 사용자 본인 확인 (국민 기준) | 기관 직원/민원인 역할 관리 |
| 다른 기관 서비스 접근 시 인증 중개 | 기관 내부 시스템 권한 관리 |
| 회원 전환(기관 계정 연결) | 기관 계정 생성/수정/삭제 |

### 2.3 연동 후 달라지는 점

**사용자 경험 변화**:
- 변경 전: 기관 아이디/비밀번호로만 로그인
- 변경 후: 기관 아이디/비밀번호 **또는** 원패스 간편 인증으로 로그인 (선택)

**기관 시스템 변화**:
- 기관 DB에 컬럼 2개 추가 (`ci_hash`, `qim_user_id`)
- API 2개 구현 (회원 조회, 매핑)
- 기관 SSO 로그인 성공 후 원패스 토큰 검증 경로 추가

## 3. 연동 방식 선택 — 3가지 옵션

기관의 상황에 따라 연동 방식을 선택합니다. 담당 연동 지원팀과 협의 후 결정하세요.

### 옵션 A: 완전 분리 (기본 권장)

```
사용자 → 원패스 인증 → 기관 콜백 → 기관 세션 생성
                                   ↕ (독립 운영)
사용자 → 기관 SSO 인증 → 기관 세션 생성
```

- **기관 SSO 변경 없음** (가장 덜 침습적)
- 사용자가 원패스 또는 기관 SSO 중 선택
- 회원 전환 기능으로 두 계정을 하나로 연결 가능
- **권장 대상**: 자체 SSO를 안정적으로 운영 중인 기관, 내부 시스템 변경 최소화가 목표인 경우

### 옵션 B: 원패스 인증 후 기관 SSO 위임

```
사용자 → 원패스 인증 완료 → [원패스 인증 성공 정보]
                               ↓
                            기관 SSO에 "원패스 인증 완료" 신호 전달
                               ↓
                            기관 SSO 세션 발급
```

- 원패스가 인증의 게이트키퍼, 기관 SSO가 세션 관리
- 기관 SSO 코드 수정 필요 (원패스 신호 수신 처리)
- **권장 대상**: 원패스를 주요 인증 수단으로 전환하면서 기관 세션 관리는 유지하고 싶은 경우

### 옵션 C: SAML/OIDC 브로커링 (향후 지원 예정)

```
기관 SSO (SAML IdP) ←──── 원패스 (SAML SP/Broker)
                              ↕
                          표준 프로토콜 연동
```

- 기관 SSO가 SAML 2.0 또는 OIDC를 지원하는 경우 표준 프로토콜로 연동
- 기관 SSO 코드 변경 최소화 (SAML 설정만 변경)
- **현재 상태**: 설계 완료, 구현 예정
- **권장 대상**: SAML 2.0 기반 SSO를 운영 중인 기관

> **현재 지원**: 옵션 A와 옵션 B를 지원합니다. 이 가이드는 주로 옵션 A를 기준으로 설명합니다.

## 4. 기관이 준비해야 하는 것

### 4.1 기관 담당자가 결정해야 할 사항

| 결정 사항 | 설명 | 담당 |
|----------|------|------|
| 연동 방식 선택 | 옵션 A / B / C 중 선택 | SSO 담당자 + 정보화 부서장 |
| 기관 코드 발급 신청 | 원패스 관리자에게 신청 | 담당자 |
| API 키 수령 | 원패스가 발급하는 API 인증 키 | 담당자 |
| 회원 전환 범위 결정 | 어떤 사용자에게 전환 기능을 제공할지 | 기관 정책 결정 |
| 본인인증 서비스 계약 | NICE/PASS 본인인증 API 이미 계약되어 있는지 확인 | 담당자 |

### 4.2 개발팀이 구현해야 하는 것

> **이 섹션을 개발팀에 전달하세요**

```
필수 구현 항목:
□ API 1: POST /api/v1/members/lookup  (identifierHash로 회원 조회)
□ API 2: POST /api/v1/members/link    (qim_user_id 매핑 저장)
□ DB 변경: ci_hash, qim_user_id 컬럼 추가

선택 구현 항목 (회원 전환 기능 제공 시):
□ 사용자 화면: 원패스 전환 버튼 및 본인인증 흐름
□ 본인인증(NICE/PASS) CI 수집 및 ci_hash 저장 로직
□ 원패스 Agency SDK 통합

Agent 설치 (원패스 토큰 검증 자동화 시):
□ idem-agent.jar JVM 설치
□ onepass-agent.properties 설정 파일 작성
```

개발 상세 사항은 **개발자 레퍼런스**(`docs/sso-agency-developer-guide.md`)를 참고하세요.

### 4.3 인프라 담당이 확인해야 하는 것

```
네트워크:
□ 기관 서버 → IdO 서버 (ido.onepass.go.kr:443) HTTPS 아웃바운드 허용
□ Q-IM 서버 → 기관 API (api/v1/members/**) 인바운드 허용 (방화벽)

서버:
□ JDK 8 이상 설치 (Agent 요구사항)
□ 기관 API 서버 TLS 인증서 설정 (HTTPS 필수)
```

## 5. 회원 전환이란 무엇인가

### 5.1 개념 설명

회원 전환은 사용자가 **기관에서 사용하던 기존 계정**과 **원패스 계정**을 **하나로 연결**하는 과정입니다.

```
전환 전:
  사용자 A ──→ 기관 SSO 계정 (아이디: user001)
  사용자 A ──→ 원패스 계정 (별개, 연결 없음)

전환 후:
  사용자 A ──→ 기관 SSO 계정 (아이디: user001)
                    ↕ 연결됨
              원패스 계정
              
  → 원패스로 로그인하면 기관 SSO 계정으로 자동 인식
```

### 5.2 전환 5단계

| 단계 | 상태 | 설명 |
|------|------|------|
| 1단계 | INITIATED | 사용자가 전환 시작 버튼 클릭 |
| 2단계 | MEMBERS_FETCHED | 원패스가 기관 `lookup` API로 기존 계정 조회 |
| 3단계 | ACCOUNT_SELECTED | 사용자가 연결할 계정 선택 (복수인 경우) |
| 4단계 | LINKING | 원패스가 기관 `link` API로 매핑 저장 |
| 5단계 | COMPLETED | 전환 완료 |

### 5.3 기관 입장에서의 전환 흐름

```
[기관 사용자 화면]
  1. "원패스 계정 연결" 버튼 클릭
  2. 본인인증 팝업 (NICE/PASS) 진행
  3. 본인인증 완료 → ci_hash 기관 DB에 저장
  4. 원패스 서버가 자동으로 기관 lookup API 호출
  5. 기관이 해당 ci_hash로 회원 조회 후 결과 반환
  6. 사용자가 연결할 계정 선택
  7. 원패스 서버가 기관 link API 호출
  8. 기관 DB에 qim_user_id 저장
  9. 전환 완료 화면
```

## 6. 본인인증과 CI 수집 — 기관이 자주 묻는 질문

### Q1. 기존 회원 수십만 명의 CI를 모두 소급 수집해야 하나요?

**아니요.** 소급 수집은 **불필요하고 권장하지 않습니다.**

원패스 연동은 사용자가 **자발적으로 원할 때** 이루어집니다. 전환을 원하는 사용자가 본인인증을 수행하는 시점에 1회 CI를 수집하면 됩니다. 전환을 원하지 않는 기존 회원은 기관 SSO를 그대로 사용하면 됩니다.

```
나쁜 방법 ❌
  → 기존 회원 100만 명 일괄 본인인증 강제
  → 관리자가 외부 시스템에서 CI 이관 시도

좋은 방법 ✅
  → 원패스 연결을 원하는 사용자만 자발적 본인인증
  → 신규 가입 시 본인인증 수행하면서 ci_hash 저장
  → 점진적으로 연결 회원 증가
```

### Q2. CI가 무엇인가요? 개인정보인가요?

CI(연계정보, Connecting Information)는 **주민등록번호로부터 파생된 식별자**입니다. 주민번호 자체는 아니지만 개인을 식별할 수 있는 정보로 **개인정보**에 해당합니다.

원패스 연동에서 사용하는 것은 CI가 아니라 `identifierHash = SHA-256(CI)`입니다. SHA-256은 단방향 함수이므로 `identifierHash`에서 CI나 주민번호를 역산할 수 없습니다.

**개인정보 처리 방침 고려사항**:
- 기관 DB에 `ci_hash` 컬럼을 추가하는 경우, 개인정보 처리방침 항목에 추가 필요
- 보존 기간, 보호 조치 등 개인정보 보호법 준수 필요
- 정보보안 부서와 사전 협의 권장

### Q3. 기관에 이미 NICE 본인인증이 있는데 별도로 또 계약해야 하나요?

아닙니다. 기관이 이미 NICE 또는 PASS 본인인증 API를 사용하고 있다면 **추가 계약 없이** 그 API에서 반환하는 CI값을 활용하면 됩니다. 기관 개발팀은 기존 본인인증 처리 코드에 `ci_hash = SHA-256(CI)` 저장 로직만 추가하면 됩니다.

### Q4. 전환하지 않은 사용자는 어떻게 되나요?

영향 없습니다. 원패스 연동은 **기존 기관 SSO와 완전히 독립적으로 공존**합니다. 전환하지 않은 사용자는 기존 기관 SSO 방식으로 계속 로그인하면 됩니다.

### Q5. 나중에 전환을 "해제"할 수 있나요?

가능합니다. 기관 DB의 `qim_user_id` 컬럼을 NULL로 초기화하면 연결이 해제됩니다. 단, 해제 후 재연결하려면 다시 본인인증을 수행해야 합니다. 해제 기능 구현은 선택사항이며, 기관 정책에 따라 결정합니다.

## 7. 연동 절차 단계별 안내

### 7.1 전체 일정 (예시)

```
1주차: 사전 준비
├── 기관 코드 발급 신청
├── API 키 수령
├── 연동 방식 결정 (옵션 A/B/C)
└── 개발팀 킥오프

2~3주차: 개발
├── DB 컬럼 추가 (ci_hash, qim_user_id)
├── lookup/link API 개발
├── 본인인증 CI 수집 로직 추가
└── Agent 설치 (선택)

4주차: 테스트
├── 개발 환경 테스트 (agency-stub 활용)
├── 전환 흐름 E2E 테스트
└── 보안 점검

5주차: 운영 적용
├── 스테이징 환경 검증
├── 운영 배포
└── 모니터링
```

### 7.2 1단계 — 사전 신청

**기관에서 제출해야 하는 정보**:

| 항목 | 예시 |
|------|------|
| 기관명 | ○○부처 산하 ××공단 |
| 기관 코드 (희망) | `AGENCY_XXXX` |
| 연동 방식 | 옵션 A (완전 분리) |
| API 서버 도메인 | `https://api.xxxx.go.kr` |
| 콜백 URL (Handoff) | `https://www.xxxx.go.kr/onepass/callback` |
| 담당자 이름/연락처 | 홍길동 / 010-0000-0000 |
| 개발 완료 예상일 | 2026-06-30 |

**수령하는 정보**:
- `기관 코드` (X-Agency-Code 헤더용)
- `API 키` (X-Agency-Key 헤더용)
- `HMAC 비밀키` (서명 검증용, 별도 발급)
- `개발 환경 URL` (테스트용 IdO 서버 주소)

### 7.3 2단계 — 개발 (개발팀 전달 사항)

개발팀에 다음 문서를 전달하세요:
- 이 문서 (SSO 담당자 가이드)
- `docs/sso-agency-developer-guide.md` (개발자 레퍼런스)
- 발급받은 기관 코드, API 키, HMAC 키, 개발 환경 URL

**담당자가 확인할 체크포인트**:
```
□ DB 변경 완료 (ci_hash, qim_user_id 컬럼 추가)
□ lookup API 응답 속도 15초 이내 확인
□ link API 멱등성 확인 (동일 요청 재호출 시 동일 응답)
□ HTTPS 인증서 설치 확인
□ 방화벽 인바운드 규칙 추가 (Q-IM 서버 IP 허용)
```

### 7.4 3단계 — 테스트

**담당자 확인 시나리오**:

```
시나리오 1: 신규 사용자
  1. 기관에 신규 가입 (본인인증 포함)
  2. ci_hash가 DB에 저장되었는지 확인
  3. 원패스 앱에서 해당 기관 계정 연결 시도
  4. 연결 완료 후 qim_user_id 저장 확인

시나리오 2: 기존 사용자 (ci_hash 없음)
  1. 기존 회원이 "원패스 계정 연결" 버튼 클릭
  2. 본인인증 팝업 진행
  3. 본인인증 완료 후 ci_hash 저장 확인
  4. 원패스 계정 연결 완료 확인

시나리오 3: 원패스로 로그인
  1. 기관 웹사이트에서 "원패스로 로그인" 클릭
  2. 원패스 인증 완료
  3. 기관 세션에 기관 계정 정보 로드 확인
```

### 7.5 4단계 — 운영 반영

- 운영 환경 기관 코드/API 키 교체 (개발용과 운영용 분리)
- 모니터링 설정 (섹션 10 참조)
- 사용자 안내문 준비 ("원패스 계정 연결 방법" 공지)

## 8. 기관 SSO 시스템 변경 최소화 전략

### 8.1 최소 변경 원칙

기관 SSO 코드를 최대한 건드리지 않는 전략입니다.

```
변경 최소화 접근법:
  1. 기관 SSO 코드 → 건드리지 않음
  2. DB에 컬럼 2개만 추가 (기존 테이블 구조 유지)
  3. 신규 API 서버 또는 엔드포인트만 추가
  4. 원패스 Agent는 별도 JAR로 JVM에 주입 (기존 코드 변경 없음)
```

### 8.2 자체 SSO와 원패스 인증의 공존

```
[기관 SSO 인증 영역]        [원패스 연동 영역]
  ┌─────────────────┐       ┌─────────────────────┐
  │ 기관 로그인 페이지 │       │ 원패스 로그인 버튼    │
  │ (기존 그대로)    │       │ (신규 추가)          │
  └────────┬────────┘       └─────────┬───────────┘
           │                          │
           ▼                          ▼
  [기관 SSO 인증]              [원패스 IdO 인증]
           │                          │
           ▼                          ▼
  [기관 세션 생성]             [HandoffTicket 발급]
  (기존 방식 그대로)                   │
                                      ▼
                              [기관 콜백 처리 (신규)]
                                      │
                                      ▼
                              [기관 세션 생성 (신규)]
```

### 8.3 단계적 도입 전략

**Phase 1 (최소 연동)**: API 2개 + DB 컬럼 추가만
- 사용자 화면 변경 없음
- 원패스 관리자가 직접 테스트용 데이터로 확인

**Phase 2 (회원 전환)**: 사용자 화면 + 전환 버튼 추가
- "원패스 계정 연결" 버튼 추가
- 전환 완료 후 이중 로그인 방지 처리

**Phase 3 (원패스 로그인)**: 기관 로그인 화면에 원패스 버튼 추가
- "원패스로 로그인" 버튼 노출
- Handoff 콜백 URL 처리 구현

## 9. 완전한 연동이 불가한 경우

다음 상황에서는 기술적으로 완전한 연동이 어렵습니다. 이 경우 부분 연동 또는 대안을 고려하세요.

### 9.1 CI 미보유 기존 회원 다수

**상황**: 기존 회원 중 NICE/PASS 본인인증 이력이 없어 CI 정보가 없는 경우

**제약**: 이러한 회원은 소급하여 자동 연결이 불가합니다.

**대안**:
- 해당 사용자가 기관 서비스 이용 중 본인인증을 수행하는 시점에 연결
- 연결 촉진 캠페인 (이벤트, 인센티브 등)으로 자발적 전환 유도
- 신규 가입자부터 자동 CI 수집 (점진적 확대)

### 9.2 레거시 SSO 시스템 (LDAP만 운영)

**상황**: 기관 SSO가 LDAP만으로 구성되어 있고 API 서버가 없는 경우

**제약**: `lookup`/`link` API를 위한 HTTP 서버가 없음

**대안**:
- 별도 API 서버(Spring Boot, Node.js 등) 추가 구축 후 LDAP 조회 연동
- LDAP의 기존 속성에 `ci_hash`, `qim_user_id` 커스텀 속성 추가
- 연동 지원팀과 LDAP 연동 방안 별도 협의

### 9.3 폐쇄망 환경

**상황**: 기관 서버가 외부 인터넷과 완전히 격리된 폐쇄망

**제약**: 원패스 서버(ido.onepass.go.kr)와 직접 통신 불가

**대안**:
- 전용 회선 또는 VPN 터널 구성
- 중간 프록시 서버 구성 (기관 내부 DMZ에 위치)
- 연동 지원팀과 별도 네트워크 구성 협의

## 10. 체크리스트 — 연동 준비 완료 확인

### 10.1 사전 준비 체크리스트 (담당자)

```
□ 기관 코드 발급 신청 완료
□ API 키 수령 완료 (개발용 / 운영용 분리)
□ 연동 방식 결정 (옵션 A/B/C)
□ 개발팀 킥오프 미팅 완료
□ 방화벽 인바운드 규칙 추가 요청 완료
□ 개인정보 처리방침 업데이트 협의 (정보보안팀)
□ 본인인증(NICE/PASS) API 계약 여부 확인
```

### 10.2 개발 완료 체크리스트 (개발팀 확인 요청)

```
□ DB: ci_hash 컬럼 추가 (VARCHAR 300, 인덱스 포함)
□ DB: qim_user_id 컬럼 추가 (VARCHAR 36, 인덱스 포함)
□ API: POST /api/v1/members/lookup 구현 및 15초 이내 응답 확인
□ API: POST /api/v1/members/link 구현 및 멱등성 확인
□ HTTPS: API 서버 TLS 인증서 설치
□ 테스트: agency-stub로 E2E 테스트 완료
□ 보안: X-Agency-Key 헤더 검증 구현
□ 로그: lookup/link 호출 로그 기록 확인
```

### 10.3 운영 배포 체크리스트

```
□ 운영 환경 API 키 교체 (개발용 삭제, 운영용 적용)
□ 모니터링 알람 설정 (lookup/link API 에러율)
□ 사용자 공지 준비 ("원패스 계정 연결" 기능 안내)
□ 문제 발생 시 연락처 확보 (원패스 연동 지원팀)
□ 롤백 계획 수립 (연동 해제 시 절차)
```

### 10.4 비상 연락처

| 상황 | 연락처 |
|------|--------|
| API 키 분실/재발급 | 원패스 연동 지원팀 ☎ |
| 연동 오류 긴급 대응 | 원패스 운영팀 (24시간 On-call) |
| 기술 문의 | 연동 전담 담당자 (업무시간 내) |
| 개인정보 관련 | 원패스 개인정보 보호팀 |
