## 1. 우리 기관이 해당되는지 확인

다음 항목에 해당하는 기관이 이 가이드의 대상입니다.

| 확인 항목 | 해당 | 해당 없음 |
|----------|------|---------|
| 기관 자체 로그인 시스템(SSO, IAM, LDAP 등)을 운영 중 | ✅ | |
| 직원/사용자가 기관 아이디/비밀번호로 별도 로그인 | ✅ | |
| 원패스(공공 통합인증)와 기관 로그인을 병행 운영 예정 | ✅ | |
| 기관 SSO와 원패스를 "연결"하거나 "통합"하라는 지시를 받음 | ✅ | |

**해당 없는 경우**: 기관 자체 SSO 없이 원패스만 사용할 예정이라면, 일반 연동 가이드를 참고하세요.

## 2. 원패스 연동의 의미 — 기관 SSO와 무엇이 다른가

### 2.1 원패스는 기관 SSO를 "대체"하지 않습니다

흔한 오해입니다. 원패스는 기관 내부 SSO와 경쟁하거나 대체하는 시스템이 아닙니다.

```
[오해] 원패스 → 기관 SSO 폐지 → 원패스로 단일 통합
[실제] 원패스 + 기관 SSO 공존 → 원패스가 "외부 인증 경로" 추가
```

### 2.2 원패스가 하는 일

| 원패스 담당 | 기관 SSO 담당 |
|------------|-------------|
| 공공기관 간 통합 인증 | 기관 내부 사용자 인증 |
| 사용자 본인 확인 (국민 기준) | 기관 직원/민원인 역할 관리 |
| 다른 기관 서비스 접근 시 인증 중개 | 기관 내부 시스템 권한 관리 |
| 로그인 어설션(식별자·속성·역할) 전달, 로그아웃·탈퇴 이벤트 통보 | 기관 계정 생성/수정/삭제, 기존 계정과의 연결 |

### 2.3 연동 후 달라지는 점

**사용자 경험 변화**:
- 변경 전: 기관 아이디/비밀번호로만 로그인
- 변경 후: 기관 아이디/비밀번호 **또는** 원패스 간편 인증으로 로그인 (선택)

**기관 시스템 변화**:
- 기관 DB에 컬럼 1개 추가 (`onepass_subject_id` — 원패스가 준 기관별 식별자)
- API 2개 구현 (회원 조회, 매핑)
- 기관 SSO 로그인 성공 후 원패스 토큰 검증 경로 추가

## 3. 연동 방식 선택 — 3가지 옵션

기관의 상황에 따라 연동 방식을 선택합니다. 담당 연동 지원팀과 협의 후 결정하세요.

### 옵션 A: 완전 분리 (기본 권장)

```
사용자 → 원패스 인증 → 기관 콜백 → 기관 세션 생성
                                   ↕ (독립 운영)
사용자 → 기관 SSO 인증 → 기관 세션 생성
```

- **기관 SSO 변경 없음** (가장 덜 침습적)
- 사용자가 원패스 또는 기관 SSO 중 선택
- 첫 로그인 때 기존 기관 계정과 연결 가능(§5)
- **권장 대상**: 자체 SSO를 안정적으로 운영 중인 기관, 내부 시스템 변경 최소화가 목표인 경우

### 옵션 B: 원패스 인증 후 기관 SSO 위임

```
사용자 → 원패스 인증 완료 → [원패스 인증 성공 정보]
                               ↓
                            기관 SSO에 "원패스 인증 완료" 신호 전달
                               ↓
                            기관 SSO 세션 발급
```

- 원패스가 인증의 게이트키퍼, 기관 SSO가 세션 관리
- 기관 SSO 코드 수정 필요 (원패스 신호 수신 처리)
- **권장 대상**: 원패스를 주요 인증 수단으로 전환하면서 기관 세션 관리는 유지하고 싶은 경우

### 옵션 C: 표준 OIDC (OIDC_RP) — 기관이 표준 Relying Party 로 붙는다

```
기관 서비스 (OIDC RP)  ──authorization code + PKCE──▶  Idem OIDC Provider (gate 공개 URL/realms/idem)
        ▲                                                   │ 토큰 교환 시 Idem 정책 판정(점검·인증수준·제공자·상태·할당)
        └──────── id_token · access_token · userinfo(idem_*) ◀┘
```

- 기관은 **issuer · client_id · client_secret** 셋만 받는다. `{issuer}/.well-known/openid-configuration` 이 나머지를 알려 준다.
- Spring Security(`spring-boot-starter-oauth2-client`)·Keycloak 어댑터·passport 등 표준 OIDC 라이브러리를 그대로 쓴다. 기관 코드 수정은 OIDC 설정뿐이다.
- 허용 범위: `response_type=code`, PKCE `S256` 필수, `client_secret_basic|post`, `RS256`. implicit·password·device 는 없다.
- Idem 클레임: id_token/access_token 에 `identity_provider`(본인확인 경로)·`acr`(인증수준)·`idem_service`, userinfo 에 `idem_state(APPROVED|GUEST)`·`idem_subject`(프로파일 `identity.subjectScheme` 의 기관향 식별자, 기본 PAIRWISE)·`idem_subject_scheme`·`idem_roles`·`idem_assigned`·`idem_user_id`. 옵션 A 의 Handoff 어설션과 같은 어휘다.
- 정책은 우회할 수 없다: 토큰 교환이 `403 access_denied` 로 끝나면 `error_description` 첫 토큰이 사유 코드다(`E-IDO-120` 미할당 등). 사용자 상태·할당이 뒤에 바뀌면 다음 userinfo 호출이 403 이 된다.
- 로그아웃: RP-Initiated Logout(`end_session_endpoint`, `id_token_hint` 필수) 과 Back-Channel Logout(프로파일 `protocol.oidc.backchannelLogoutUri` 로 `logout_token` POST — `sid` 로 기관 세션을 끊으세요) 지원. Idem 쪽 세션 종료(관리자·다른 서비스의 로그아웃)도 같은 Back-Channel 로 옵니다.
- 참조 구현: `idem-tenant-sample` 의 `idem.sample.protocol=OIDC_RP` 경로(`/agency/oidc/login·callback·logout·backchannel-logout`, `OidcRelyingPartyClient`) — 라이브러리 없이 필요한 검증을 전부 보여 줍니다. Spring Security OAuth2 Client 등 표준 라이브러리를 써도 같습니다.
- **권장 대상**: 표준 OIDC 를 지원하는 기관 SSO/프레임워크. SAML 2.0 은 설계만 있고 구현 예정이다.

> **현재 지원**: 옵션 A·B·C 를 지원합니다. 이 가이드는 주로 옵션 A(Handoff)를 기준으로 설명하며, 옵션 C 의 온보딩은 `docs/install.md` §5.1 을 따릅니다.

## 4. 기관이 준비해야 하는 것

### 4.1 기관 담당자가 결정해야 할 사항

| 결정 사항 | 설명 | 담당 |
|----------|------|------|
| 연동 방식 선택 | 옵션 A / B / C 중 선택 | SSO 담당자 + 정보화 부서장 |
| 기관 코드 발급 신청 | 원패스 관리자에게 신청 | 담당자 |
| API 키 수령 | 원패스가 발급하는 API 인증 키 | 담당자 |
| 계정 연결 기준 결정 | 기존 계정과 어떤 속성(이메일·사번 등)으로 연결할지, 자동/수동 | 기관 정책 결정 |
| 본인인증 서비스 계약 | NICE/PASS 본인인증 API 이미 계약되어 있는지 확인 | 담당자 |

### 4.2 개발팀이 구현해야 하는 것

> **이 섹션을 개발팀에 전달하세요**

```
필수 구현 항목:
□ 로그인 완료 처리: 원패스 Handoff verify(또는 SDK) 로 어설션을 받아 기관 세션 생성
□ DB 변경: 기관 사용자 테이블에 onepass_subject_id 컬럼 추가 (원패스가 준 기관별 식별자, 인덱스)
□ 계정 연결: 첫 로그인 때 기존 계정을 찾아 onepass_subject_id 를 기록 (§5)

선택 구현 항목:
□ 이벤트 수신(웹훅): 로그아웃·탈퇴·정지 이벤트를 받아 기관 세션·계정 상태 반영
□ 원패스 Agency SDK 통합

Agent 설치 (원패스 토큰 검증 자동화 시):
□ idem-agent.jar JVM 설치
□ onepass-agent.properties 설정 파일 작성
```

원패스는 기관 서버의 API 를 호출해 회원을 조회하거나 등록하지 **않습니다**. 기관이 열어야 하는 인바운드 API 는 (선택) 이벤트 웹훅뿐입니다.

개발 상세 사항은 **개발자 레퍼런스**(`docs/sso-agency-developer-guide.md`)를 참고하세요.

### 4.3 인프라 담당이 확인해야 하는 것

```
네트워크:
□ 기관 서버 → IdO 서버 (예: idem.hub.example.org:443) HTTPS 아웃바운드 허용
□ Q-IM 서버 → 기관 API (api/v1/members/**) 인바운드 허용 (방화벽)

서버:
□ JDK 8 이상 설치 (Agent 요구사항)
□ 기관 API 서버 TLS 인증서 설정 (HTTPS 필수)
```

## 5. 기존 계정 연결 — 기관 측 첫 로그인 연결

### 5.1 개념 설명

원패스로 로그인한 사용자와 기관이 이미 갖고 있던 계정을 **하나로 잇는 일은 기관 쪽에서, 첫 로그인 때** 합니다. 원패스는 기관마다 고정된 **기관별 식별자**(`subject.agencySubjectId`, 다른 기관과 겹치지 않는 가명)와 기관 프로파일에서 허용한 **속성**(이메일·마스킹 성명·출생연도 등)을 어설션에 담아 줍니다.

```
첫 로그인:
  원패스 → 기관: { agencySubjectId: "abc…", attributes: { email: "user@x.org", … } }
  기관:   onepass_subject_id = "abc…" 인 계정이 있나?
            ├─ 있음 → 그 계정으로 로그인
            └─ 없음 → 연결 기준(이메일·사번 등)으로 기존 계정을 찾아 onepass_subject_id 기록
                       못 찾으면 신규 계정 생성 또는 사용자에게 기존 아이디/비밀번호 1회 입력 요청

이후 로그인:
  onepass_subject_id 로 즉시 매칭 (속성 대조 불필요)
```

### 5.2 연결 기준 3가지

| 방식 | 언제 | 비고 |
|------|------|------|
| 자동 연결 (속성 대조) | 기관 DB 에 이메일·사번 같은 **고유 속성**이 있고, 원패스 프로파일이 그 속성을 제공하도록 설정된 경우 | 대조 속성은 기관 프로파일 `identity.attributes` 로 요청. 연계정보(CI) 는 원패스가 내보내지 않음 |
| 수동 연결 (1회 인증) | 고유 속성이 없거나 중복 가능성이 있는 경우 | 첫 로그인 화면에서 기존 아이디/비밀번호를 1회 입력받아 연결 |
| 일회성 이관 | 기존 회원이 많고 사전에 연결하고 싶은 경우 | 원패스 이관 도구(로드맵 S9)로 오프라인 매핑 파일을 만들어 일괄 등록 |

### 5.3 기관 입장에서의 흐름

```
[기관 사용자 화면]
  1. "원패스로 로그인" 클릭 → 원패스 인증
  2. 기관 서버가 Handoff verify 로 어설션 수신
  3. onepass_subject_id 매칭 → 있으면 로그인 완료
  4. 없으면 연결 기준으로 기존 계정 탐색 → 연결 기록
  5. 로그인 완료
```

연결 해제는 기관 DB 의 `onepass_subject_id` 를 NULL 로 바꾸면 됩니다.

## 6. 본인인증과 CI 수집 — 기관이 자주 묻는 질문

### Q1. 기존 회원 수십만 명의 CI를 모두 소급 수집해야 하나요?

**아니요.** 소급 수집은 **불필요하고 권장하지 않습니다.**

원패스 연동은 사용자가 **원패스로 로그인할 때** 이루어집니다. 본인인증은 원패스 쪽에서 수행하며, 기관은 CI 를 수집·보관할 필요가 없습니다(§5). 원패스를 쓰지 않는 기존 회원은 기관 SSO를 그대로 사용하면 됩니다.

```
나쁜 방법 ❌
  → 기존 회원 100만 명 일괄 본인인증 강제
  → 관리자가 외부 시스템에서 CI 이관 시도

좋은 방법 ✅
  → 원패스로 로그인하는 사용자만 첫 로그인 때 계정 연결
  → 사전 연결이 꼭 필요하면 이관 도구(S9)로 오프라인 매핑
  → 점진적으로 연결 회원 증가
```

### Q2. CI가 무엇인가요? 개인정보인가요?

CI(연계정보, Connecting Information)는 **주민등록번호로부터 파생된 식별자**입니다. 주민번호 자체는 아니지만 개인을 식별할 수 있는 정보로 **개인정보**에 해당합니다.

원패스는 CI 를 기관에 **내보내지 않습니다**. 기관이 받는 것은 기관별 가명 식별자(`agencySubjectId`)와 프로파일에서 허용한 속성뿐이며, 이 식별자는 다른 기관과 대조할 수 없습니다.

**개인정보 처리 방침 고려사항**:
- 기관이 자체 목적으로 CI 를 보관한다면 개인정보 처리방침 항목에 추가 필요 (원패스 연동 자체는 CI 보관을 요구하지 않음)
- 보존 기간, 보호 조치 등 개인정보 보호법 준수 필요
- 정보보안 부서와 사전 협의 권장

### Q3. 기관에 이미 NICE 본인인증이 있는데 별도로 또 계약해야 하나요?

아닙니다. 원패스 로그인의 본인인증은 원패스가 수행합니다. 기관이 자체 서비스에서 별도로 본인인증이 필요하다면 기존 계약을 그대로 쓰면 되고, 원패스 연동을 위해 CI 를 저장할 필요는 없습니다.

### Q4. 원패스로 로그인하지 않는 사용자는 어떻게 되나요?

영향 없습니다. 원패스 연동은 **기존 기관 SSO와 완전히 독립적으로 공존**합니다. 원패스를 쓰지 않는 사용자는 기존 기관 SSO 방식으로 계속 로그인하면 됩니다.

### Q5. 나중에 연결을 "해제"할 수 있나요?

가능합니다. 기관 DB의 `onepass_subject_id` 컬럼을 NULL로 초기화하면 연결이 해제됩니다. 재연결은 다음 원패스 로그인 때 §5 절차로 다시 이루어집니다. 해제 기능 구현은 선택사항이며, 기관 정책에 따라 결정합니다.

## 7. 연동 절차 단계별 안내

### 7.1 전체 일정 (예시)

```
1주차: 사전 준비
├── 기관 코드 발급 신청
├── API 키 수령
├── 연동 방식 결정 (옵션 A/B/C)
└── 개발팀 킥오프

2~3주차: 개발
├── DB 컬럼 추가 (onepass_subject_id)
├── 첫 로그인 계정 연결 개발
├── 본인인증 CI 수집 로직 추가
└── Agent 설치 (선택)

4주차: 테스트
├── 개발 환경 테스트 (agency-stub 활용)
├── 로그인·계정 연결 E2E 테스트
└── 보안 점검

5주차: 운영 적용
├── 스테이징 환경 검증
├── 운영 배포
└── 모니터링
```

### 7.2 1단계 — 사전 신청

**기관에서 제출해야 하는 정보**:

| 항목 | 예시 |
|------|------|
| 기관명 | ○○부처 산하 ××공단 |
| 기관 코드 (희망) | `AGENCY_XXXX` |
| 연동 방식 | 옵션 A (완전 분리) |
| API 서버 도메인 | `https://api.xxxx.go.kr` |
| 콜백 URL (Handoff) | `https://www.xxxx.go.kr/onepass/callback` |
| 담당자 이름/연락처 | 홍길동 / 010-0000-0000 |
| 개발 완료 예상일 | 2026-06-30 |

**수령하는 정보**:
- `기관 코드` (X-Agency-Code 헤더용)
- `API 키` (X-Agency-Key 헤더용)
- `HMAC 비밀키` (서명 검증용, 별도 발급)
- `개발 환경 URL` (테스트용 IdO 서버 주소)

### 7.3 2단계 — 개발 (개발팀 전달 사항)

개발팀에 다음 문서를 전달하세요:
- 이 문서 (SSO 담당자 가이드)
- `docs/sso-agency-developer-guide.md` (개발자 레퍼런스)
- 발급받은 기관 코드, API 키, HMAC 키, 개발 환경 URL

**담당자가 확인할 체크포인트**:
```
□ DB 변경 완료 (onepass_subject_id 컬럼 추가)
□ 계정 연결 멱등성 확인 (같은 사용자 재로그인 시 같은 계정)
□ HTTPS 인증서 설치 확인
□ 방화벽 인바운드 규칙 추가 (Q-IM 서버 IP 허용)
```

### 7.4 3단계 — 테스트

**담당자 확인 시나리오**:

```
시나리오 1: 신규 사용자
  1. 기관에 신규 가입 (본인인증 포함)
  2. onepass_subject_id 가 DB에 저장되었는지 확인
  3. 원패스 앱에서 해당 기관 계정 연결 시도
  4. 연결 완료 후 qim_user_id 저장 확인

시나리오 2: 기존 사용자 (onepass_subject_id 없음)
  1. 기존 회원이 "원패스 계정 연결" 버튼 클릭
  2. 본인인증 팝업 진행
  3. 첫 로그인 연결 후 onepass_subject_id 저장 확인
  4. 원패스 계정 연결 완료 확인

시나리오 3: 원패스로 로그인
  1. 기관 웹사이트에서 "원패스로 로그인" 클릭
  2. 원패스 인증 완료
  3. 기관 세션에 기관 계정 정보 로드 확인
```

### 7.5 4단계 — 운영 반영

- 운영 환경 기관 코드/API 키 교체 (개발용과 운영용 분리)
- 모니터링 설정 (섹션 10 참조)
- 사용자 안내문 준비 ("원패스 계정 연결 방법" 공지)

## 8. 기관 SSO 시스템 변경 최소화 전략

### 8.1 최소 변경 원칙

기관 SSO 코드를 최대한 건드리지 않는 전략입니다.

```
변경 최소화 접근법:
  1. 기관 SSO 코드 → 건드리지 않음
  2. DB에 컬럼 2개만 추가 (기존 테이블 구조 유지)
  3. 신규 API 서버 또는 엔드포인트만 추가
  4. 원패스 Agent는 별도 JAR로 JVM에 주입 (기존 코드 변경 없음)
```

### 8.2 자체 SSO와 원패스 인증의 공존

```
[기관 SSO 인증 영역]        [원패스 연동 영역]
  ┌─────────────────┐       ┌─────────────────────┐
  │ 기관 로그인 페이지 │       │ 원패스 로그인 버튼    │
  │ (기존 그대로)    │       │ (신규 추가)          │
  └────────┬────────┘       └─────────┬───────────┘
           │                          │
           ▼                          ▼
  [기관 SSO 인증]              [원패스 IdO 인증]
           │                          │
           ▼                          ▼
  [기관 세션 생성]             [HandoffTicket 발급]
  (기존 방식 그대로)                   │
                                      ▼
                              [기관 콜백 처리 (신규)]
                                      │
                                      ▼
                              [기관 세션 생성 (신규)]
```

### 8.3 단계적 도입 전략

**Phase 1 (최소 연동)**: API 2개 + DB 컬럼 추가만
- 사용자 화면 변경 없음
- 원패스 관리자가 직접 테스트용 데이터로 확인

**Phase 2 (계정 연결)**: 첫 로그인 연결 화면 추가
- "원패스 계정 연결" 버튼 추가
- 연결 완료 후 이중 로그인 방지 처리

**Phase 3 (원패스 로그인)**: 기관 로그인 화면에 원패스 버튼 추가
- "원패스로 로그인" 버튼 노출
- Handoff 콜백 URL 처리 구현

## 9. 완전한 연동이 불가한 경우

다음 상황에서는 기술적으로 완전한 연동이 어렵습니다. 이 경우 부분 연동 또는 대안을 고려하세요.

### 9.1 CI 미보유 기존 회원 다수

**상황**: 기존 회원 중 NICE/PASS 본인인증 이력이 없어 CI 정보가 없는 경우

**제약**: 이러한 회원은 소급하여 자동 연결이 불가합니다.

**대안**:
- 해당 사용자가 기관 서비스 이용 중 본인인증을 수행하는 시점에 연결
- 연결 촉진 캠페인 (이벤트, 인센티브 등)으로 원패스 로그인 유도
- 신규 가입자부터 자동 CI 수집 (점진적 확대)

### 9.2 레거시 SSO 시스템 (LDAP만 운영)

**상황**: 기관 SSO가 LDAP만으로 구성되어 있고 API 서버가 없는 경우

**제약**: 어설션을 받아 세션을 만들 HTTP 서버가 없음

**대안**:
- 별도 API 서버(Spring Boot, Node.js 등) 추가 구축 후 LDAP 조회 연동
- LDAP의 기존 속성에 `onepass_subject_id` 커스텀 속성 추가
- 연동 지원팀과 LDAP 연동 방안 별도 협의

### 9.3 폐쇄망 환경

**상황**: 기관 서버가 외부 인터넷과 완전히 격리된 폐쇄망

**제약**: Idem 서버(예: idem.hub.example.org)와 직접 통신 불가

**대안**:
- 전용 회선 또는 VPN 터널 구성
- 중간 프록시 서버 구성 (기관 내부 DMZ에 위치)
- 연동 지원팀과 별도 네트워크 구성 협의

## 10. 체크리스트 — 연동 준비 완료 확인

### 10.1 사전 준비 체크리스트 (담당자)

```
□ 기관 코드 발급 신청 완료
□ API 키 수령 완료 (개발용 / 운영용 분리)
□ 연동 방식 결정 (옵션 A/B/C)
□ 개발팀 킥오프 미팅 완료
□ 방화벽 인바운드 규칙 추가 요청 완료
□ 개인정보 처리방침 업데이트 협의 (정보보안팀)
□ 본인인증(NICE/PASS) API 계약 여부 확인
```

### 10.2 개발 완료 체크리스트 (개발팀 확인 요청)

```
□ DB: onepass_subject_id 컬럼 추가 (VARCHAR 100, 인덱스 포함)
□ DB: qim_user_id 컬럼 추가 (VARCHAR 36, 인덱스 포함)
□ 로그인: Handoff verify 로 어설션 수신·세션 생성 확인
□ API: POST /api/v1/members/link 구현 및 멱등성 확인
□ HTTPS: API 서버 TLS 인증서 설치
□ 테스트: agency-stub로 E2E 테스트 완료
□ 보안: X-Agency-Key 헤더 검증 구현
□ 로그: 로그인·계정 연결 로그 기록 확인
```

### 10.3 운영 배포 체크리스트

```
□ 운영 환경 API 키 교체 (개발용 삭제, 운영용 적용)
□ 모니터링 알람 설정 (verify 실패율)
□ 사용자 공지 준비 ("원패스 계정 연결" 기능 안내)
□ 문제 발생 시 연락처 확보 (원패스 연동 지원팀)
□ 롤백 계획 수립 (연동 해제 시 절차)
```

### 10.4 비상 연락처

| 상황 | 연락처 |
|------|--------|
| API 키 분실/재발급 | 원패스 연동 지원팀 ☎ |
| 연동 오류 긴급 대응 | 원패스 운영팀 (24시간 On-call) |
| 기술 문의 | 연동 전담 담당자 (업무시간 내) |
| 개인정보 관련 | 원패스 개인정보 보호팀 |
