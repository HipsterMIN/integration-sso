1
기관 브라우저 → SDK 준비 및 correlationId 생성
Agency-Stub
▶

유관기관 서버는 AgencyGatewayClient SDK를 사용해 OnePass 플랫폼과 통신합니다. SDK는 Builder 패턴으로 초기화되며, 모든 요청에 X-Agency-Key, X-Agency-Code, X-Idempotency-Key, X-Internal-Sig(HMAC-SHA256) 헤더를 자동 첨부합니다.

AgencyGatewayClient.java — SDK 초기화 agency-stub
// SDK Builder 패턴 초기화 (Spring Bean으로 등록)
@Bean
public AgencyGatewayClient agencyGatewayClient() {
    return AgencyGatewayClient.builder()
        .baseUrl("https://ido.onepass.kr")
        .agencyCode("AGENCY_STUB_001")
        .agencyApiKey(agencyApiKey)       // X-Agency-Key
        .hmacSecret(hmacSecret)           // HMAC-SHA256 서명 키
        .connectTimeoutMs(3000)
        .readTimeoutMs(8000)
        .build();
}

// ── SDK 3대 핵심 메서드 ───────────────────────────────────────
// sendInbound()    : 기관 → OnePass 인바운드 이벤트 전송 (사용자 인증 요청 등)
// triggerOutbound(): OnePass → 기관 아웃바운드 알림 트리거 요청
// getStatus()      : 특정 correlationId의 처리 상태 조회

// 내부적으로 buildHeaders()가 매 요청마다 자동 호출
private HttpHeaders buildHeaders(String method, String path,
                                     String body, String idempotencyKey) {
    long ts = System.currentTimeMillis();
    String sig = hmacSigner.sign(method, path, ts, body);
    HttpHeaders h = new HttpHeaders();
    h.set("X-Agency-Key",        agencyApiKey);
    h.set("X-Agency-Code",       agencyCode);
    h.set("X-Idempotency-Key",   idempotencyKey);
    h.set("X-Correlation-Id",    correlationId);
    h.set("X-Internal-Sig",      sig);
    h.set("X-Timestamp",          String.valueOf(ts));
    return h;
}
HmacSigner.java — HMAC-SHA256 서명 SDK
// 서명 대상 문자열 구성
// "METHOD\nPATH\nTIMESTAMP_EPOCH_MS\nSHA256(body)"
public String sign(String httpMethod, String path,
                    long timestampMs, String requestBody) {
    String bodyHash = sha256Hex(requestBody != null ? requestBody : "");
    String signingString = httpMethod + "\n" + path
                            + "\n" + timestampMs
                            + "\n" + bodyHash;
    return hmacSha256Hex(signingString);
}

// 서명 검증 — 상수시간 비교로 timing attack 방지
public boolean verifySignature(String received, String expected) {
    return MessageDigest.isEqual(
        received.getBytes(StandardCharsets.UTF_8),
        expected.getBytes(StandardCharsets.UTF_8)
    );
}

BrokerService.buildAuthorizationUrl() — qsign / keycloak 모드 분기
Logic
▶

brokerMode 설정에 따라 두 가지 경로로 분기됩니다. qsign 모드는 Q-Sign 서비스에 URL 생성을 위임하고, keycloak 모드는 IdO가 직접 Keycloak URL을 생성합니다.

BrokerService.java — 모드 분기 IdO
public String buildAuthorizationUrl(String provider,
        String returnUrl, String correlationId, String agencyCode) {

    return switch (brokerMode) {
        case "qsign" -> buildViaQSign(provider, returnUrl, correlationId);
        case "keycloak" -> buildDirectKeycloakUrl(provider, returnUrl, correlationId);
        default -> throw new IllegalStateException("Unknown brokerMode: " + brokerMode);
    };
}

// ── qsign 모드: Q-Sign에 URL 생성 위임 ─────────────────────
private String buildViaQSign(String provider,
        String returnUrl, String correlationId) {
    String ts = String.valueOf(Instant.now().getEpochSecond());
    String sig = computeInternalSig(correlationId, ts);  // HMAC-SHA256

    // POST q-sign/api/v1/oidc/{provider}/auth-url
    return qSignClient.getAuthorizationUrl(provider, returnUrl,
            correlationId, sig, ts);
}

// ── keycloak 모드: IdO가 직접 URL 생성 ──────────────────────
private String buildDirectKeycloakUrl(String provider,
        String returnUrl, String correlationId) {
    String state = generateState(correlationId);   // CSRF 방지용
    String nonce = generateNonce();                // 재사용 방지
    // Redis에 state, nonce, returnUrl 저장 (TTL 10분)
    idoOidcStateStore.create(state, nonce, returnUrl, correlationId);

    return UriComponentsBuilder
            .fromHttpUrl(keycloakAuthEndpoint)
            .queryParam("client_id",     kcClientId)
            .queryParam("response_type", "code")
            .queryParam("scope",         "openid profile")
            .queryParam("state",         state)
            .queryParam("nonce",         nonce)
            .queryParam("kc_idp_hint",  "social-kakao")  // IdP 직접 지정
            .queryParam("redirect_uri",  qSignCallbackUrl)
            .toUriString();
}

// X-Internal-Sig: HMAC-SHA256(correlationId + ":" + epochSeconds, secret)
private String computeInternalSig(String correlationId, String ts) {
    return hmacSha256Hex(correlationId + ":" + ts, internalSigningSecret);
}
kc_idp_hint 역할: Keycloak 로그인 선택 화면을 건너뛰고 지정된 소셜 IdP (social-kakao)로 직행시킵니다. 사용자 UX 개선 핵심 파라미터.

Phase 2 — Keycloak OIDC + 카카오 OAuth2 인증

브라우저가 Keycloak → 카카오 → 사용자 인증 → Q-Sign 콜백까지 도달하는 과정.

1
Keycloak Authorization Endpoint 처리
Keycloak
▶

브라우저가 Keycloak Authorization Endpoint에 도달합니다. kc_idp_hint=social-kakao가 있으므로 로그인 선택 화면을 건너뛰고 카카오 IdP Federation으로 즉시 리다이렉트합니다.

  • 1 파라미터 파싱: state, nonce, redirect_uri, kc_idp_hint 추출 kc_idp_hint = "social-kakao" → Keycloak 내부 IdP 별칭
  • 2 세션 생성: Keycloak 내부 auth session 생성 (state → Keycloak 세션 매핑)
  • 3 카카오 OAuth2 요청 생성: scope=openid profile email, Keycloak 자체 state 생성 원본 state(IdO/Q-Sign state)와 카카오용 state를 Keycloak이 내부 매핑 관리
  • 4 302 → 카카오 Authorization URL: https://kauth.kakao.com/oauth/authorize?client_id=...&state=...&redirect_uri=https://keycloak.../auth/realms/.../broker/social-kakao/endpoint

2
사용자 카카오 로그인 → 카카오 → Keycloak 콜백
사용자 인증
▶

사용자가 카카오 로그인 페이지에서 인증합니다. 카카오는 Keycloak의 콜백 URL로 code와 state를 전달합니다. Keycloak은 카카오 Token API로 code를 교환하고, 카카오 사용자 정보를 조회하여 Keycloak 내부 사용자 계정에 연결(federated identity)합니다.

  • 1 카카오 → Keycloak 콜백: GET /auth/realms/.../broker/social-kakao/endpoint?code=xxx&state=yyy
  • 2 Keycloak 내부: POST https://kapi.kakao.com/oauth/token → access_token 교환
  • 3 카카오 사용자 정보 조회: GET https://kapi.kakao.com/v2/user/me → sub(카카오 고유 ID) 획득
  • 4 Keycloak 사용자 연결: federated identity 매핑. 최초 로그인이면 Keycloak 사용자 생성(또는 기존 계정 연결). sub = 카카오 고유 ID가 Keycloak identity provider link의 userId로 저장됨
  • 5 OIDC id_token 발급: Keycloak이 원래 OAuth2 요청(redirect_uri=Q-Sign)으로 code + state 담아 302 → Q-Sign 콜백

Phase 3 — Q-Sign KeycloakCallbackService 처리 (11단계)

가장 복잡한 단계. CSRF→토큰교환→JWKS검증→DB저장→IdO통보까지 @Transactional 내부 처리.

1
handleCallback() — state 소비 (CSRF 원샷 검증)
RedisCSRF
▶

state 파라미터는 1회성 토큰입니다. Redis에서 consumeAndValidate(state)를 호출하여 존재 여부를 확인하고 즉시 삭제합니다. 이로써 CSRF(Cross-Site Request Forgery) 공격과 콜백 재사용 공격을 모두 차단합니다.

KeycloakCallbackService.java — state 소비 Q-Sign
public String handleCallback(String code, String state) {

    // ① state 소비 (Redis DEL + 존재 확인) — CSRF 방지
    OidcStateEntry stateEntry = stateStore.consumeAndValidate(state);
    // stateEntry에 nonce, returnUrl, correlationId 포함
    // state가 없거나 이미 소비된 경우 → InvalidStateException 발생

    String correlationId = stateEntry.getCorrelationId();
    String returnUrl    = stateEntry.getReturnUrl();
    // ...
}
보안 포인트: stateStore.consumeAndValidate()는 Redis GET + DEL을 Lua 스크립트로 원자적으로 실행합니다. 분산 환경에서도 두 인스턴스가 동시에 같은 state를 처리하는 경쟁 조건이 발생하지 않습니다.

3
JWKS RS256 검증 → nonce / aud / exp → SHA-256(sub)
Security
▶

수신한 id_token을 5단계로 철저히 검증합니다. Keycloak의 JWKS 엔드포인트에서 공개키를 조회하여 서명을 검증하고, 모든 클레임이 유효한지 확인합니다.

  • ① JWKS 공개키 조회: GET {keycloak}/.well-known/jwks.json → kid 매칭 → RS256 공개키 로드 (로컬 캐시, 5분 TTL)
  • ② 서명 검증: JWT Header + Payload를 공개키로 RS256 서명 검증. 위조된 id_token 즉시 거부.
  • ③ nonce 검증: id_token.nonce == stateEntry.nonce 일치 확인. 재사용 공격 방지. nonce도 Redis에 1회성으로 저장되어 있으며, 이미 state 소비 시 함께 읽힘
  • ④ aud 검증: id_token.aud == kcClientId 확인. 타 클라이언트 토큰 재사용 방지.
  • ⑤ exp 검증: 토큰 만료 시각 > 현재 시각. 만료 토큰 거부.
  • ⑥ SHA-256(sub) = identifierHash: sub는 Keycloak 내부 사용자 UUID. SHA-256 해시로 저장 → 원본 sub 비노출 보호. identifierHash가 Q-IM의 CI(개인연계정보)에 해당하는 식별자.
  • ⑦ providerCode 역매핑: Keycloak IdP 별칭 social-kakao → 내부 코드 KAKAO_OIDC (provider_code_mapping 테이블 조회)
  • ⑧ lockRepository.isLocked(identifierHash): 해당 사용자가 보안상 Lock 상태인지 확인. Lock이면 AUTH_LOCKED 처리.

@Transactional — authResultRepo.save() + outboxRepo.save()
DB TXOutbox
▶

검증이 완료되면 하나의 트랜잭션 내에서 인증 결과와 Outbox 레코드를 동시에 저장합니다. 이것이 Transactional Outbox Pattern의 핵심입니다. DB 커밋이 성공해야만 Kafka 이벤트 발행이 보장됩니다.

KeycloakCallbackService.java — @Transactional 저장 Q-Sign
@Transactional
private AuthResult issueAuthResult(String identifierHash,
        String providerCode, String nonce,
        AuthResult.AuthLevel authLevel, String correlationId) {

    // ① AuthResult 저장 → qsign.auth_result 테이블
    AuthResult result = AuthResult.builder()
            .authResultId(UuidV7.generate())
            .identifierHash(identifierHash)  // SHA-256(sub)
            .providerCode(providerCode)       // KAKAO_OIDC
            .authLevel(authLevel)             // L1/L2/L3
            .correlationId(correlationId)
            .issuedAt(Instant.now())
            .build();
    authResultRepository.save(result);   // → qsign.auth_result

    // ② Outbox 레코드 저장 → qsign.outbox (status=PENDING)
    // 이 트랜잭션이 커밋되어야 Relay가 Kafka에 발행
    QSignOutboxRecord outbox = QSignOutboxRecord.builder()
            .eventId(UuidV7.generate())
            .eventType("AUTH_COMPLETED")
            .authResultId(result.getAuthResultId())
            .correlationId(correlationId)
            .status("PENDING")
            .build();
    outboxRepository.save(outbox);       // → qsign.outbox

    return result;
}
왜 트랜잭션 내에서 둘 다 저장해야 하는가?
만약 authResultRepository.save() 후 outboxRepository.save() 전에 프로세스가 죽으면, 인증은 완료됐지만 Kafka 이벤트가 발행되지 않아 IdO가 세션을 생성하지 못합니다. 둘을 같은 트랜잭션에 묶으면 원자성이 보장됩니다.

OidcCompleteController.java IdO
@PostMapping("/api/internal/v1/oidc/complete")
public ResponseEntity<OidcCompleteResponse> complete(
        @RequestBody OidcCompleteRequest req,
        @RequestHeader("X-Internal-Sig") String sig,
        @RequestHeader("X-Timestamp") String ts,
        @RequestHeader("X-Correlation-Id") String correlationId) {

    // ① X-Internal-Sig 검증 (상수시간 비교)
    String expected = hmacSha256Hex(correlationId + ":" + ts, internalSecret);
    if (!MessageDigest.isEqual(sig.getBytes(), expected.getBytes()))
        throw new UnauthorizedException("X-Internal-Sig mismatch");

    // ② returnUrl 화이트리스트 검증
    if (!feSessionService.isValidReturnUrl(req.getReturnUrl()))
        throw new BadRequestException("returnUrl not in whitelist");

    // ③ CI(identifierHash)로 Q-IM 사용자 조회
    String qimUserId;
    try {
        qimUserId = qimClient.findByCi(req.getIdentifierHash());
    } catch (UserNotFoundException e) {
        // ④ 미등록 사용자 → 자동 등록 (최초 로그인 시 1회)
        qimUserId = qimClient.registerUser(RegisterUserRequest.builder()
                .identifierHash(req.getIdentifierHash())
                .providerCode(req.getProviderCode())
                .authLevel(req.getAuthLevel())
                .correlationId(correlationId)
                .build());
    }
    // ...
}

            .lastActivityAt(now)

public void preWarm(AuthEvent event) {
    String correlationId = event.getCorrelationId();

    Map<String, Object> cacheValue = Map.of(
        "correlationId", correlationId,
        "authResultId",  event.getAuthResultId(),
        "qimUserId",     event.getQimUserId(),
        "authLevel",     event.getAuthLevel().name(),
        "providerCode",  event.getProviderCode(),
        "cachedAt",      System.currentTimeMillis()
    );

    // ido:auth_result:{correlationId} TTL=300s
    redisTemplate.opsForValue().set(
            "ido:auth_result:" + correlationId,
            cacheValue,
            Duration.ofSeconds(300)   // 5분 — Handoff TTL(60s)의 5배
    );

    // authLevel 별도 키 (Handoff 정책 체크 고속화)
    redisTemplate.opsForValue().set(
            "ido:auth_level:" + correlationId,
            event.getAuthLevel().name(),
            Duration.ofSeconds(300)
    );
    // 60,000건 × ~512 bytes = ~30 MB — Redis 메모리 충분
}
60,000명 급증 시나리오:
Pre-warming 없이: 60,000명 동시 Handoff 요청 → 60,000 DB 쿼리 → DB I/O 폭발 → 지연/장애
Pre-warming 있음: 인증 완료 시점에 Redis 적재 → Handoff 요청 시 DB 없이 Redis Hit (목표 99%) → DB 부하 차단

인스턴스 A가 dispatch_id=1 레코드를 Lock하면, 동시에 실행된 인스턴스 B는 해당 레코드를 건너뛰고 다음 레코드를 처리합니다. 중복 발송 없이 수평 확장 가능.

Replay 방어
▶

기관의 WebhookInboundController가 IdO로부터 HTTPS POST를 수신합니다. 첫 번째 방어선은 타임스탬프 검증입니다. X-Webhook-Timestamp가 현재 시각에서 ±5분을 벗어나면 즉시 거부합니다. 이는 서명이 탈취되어도 5분 이후에는 재사용 불가능하게 만드는 Replay Attack 방지입니다.
